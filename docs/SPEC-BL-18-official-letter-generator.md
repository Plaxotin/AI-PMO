# BL-18 — Генератор официальных писем по корпоративному бланку

**Версия:** 1.2 (MVP — решения для продуктива, согласование с BL1-0)
**Дата:** 2026-05-24
**Продукт:** AI PMO
**Код бэклога:** BL-18

---

## 1. Цель и результат

Пользователь (в контексте **AI PMO**, привязка к тенанту / проекту / пользователю) загружает **корпоративный бланк** в формате **DOCX**, вводит **суть письма только на русском языке** (произвольный текст), при необходимости прикладывает до **5 файлов приложений** (`.xlsx`, `.docx`, `.pdf`). Сервис формирует **итоговый DOCX** письма, свёрстанный в шаблоне бланка, готовый к подписанию с **плейсхолдерами** для ФИО и должности подписанта (без автоподстановки). В MVP пользователь **обязательно** получает **два артефакта скачивания**: (1) сам **DOCX письма**; (2) **ZIP-пакет** с именем вроде `letter-package.zip`, внутри которого **`letter.docx`** (то же собранное письмо) и **оригинальные файлы приложений** в неизменённом виде (см. §3.1).

## 2. Нефункциональные требования

| Область | Требование |
|--------|------------|
| Размещение | Вычислительный контур и хранение шаблонов/черновиков/журналов — **на территории РФ** (инфраструктура и первичное хранение данных). |
| Трансграничная передача | **Для MVP допускается** обращение к LLM-провайдерам вне РФ (например, бюджетные API вроде Kimi и аналоги), при явной **политике и согласии** на обработку и передачу **минимального набора данных** (см. §6). После MVP — целевой режим «без трансграницы» уточняется отдельно (например, Cloud.ru Foundation Models / on-prem). |
| Конфиденциальность | **Файл бланка (шаблон DOCX) никогда не передаётся в LLM** — ни целиком, ни как извлечённый XML, ни как вложение к промпту. В LLM попадают только **разрешённые текстовые поля** (см. §6). |
| Аудит | Обязателен **журнал аудита**: кто сгенерировал, какой шаблон (id/версия), время, идентификатор запроса, факт наличия приложений (имена/типы/hashes без обязательного хранения полного содержимого в логе — см. §8). |
| Форматы | **Вход:** шаблон — только **DOCX**; суть — **русский текст**; приложения — до **5** файлов: **`.xlsx`**, **`.docx`**, **`.pdf`**. **Выход (MVP):** **DOCX письма** + **ZIP** (`letter.docx` внутри архива + оригиналы приложений; см. §3.1). |
| Лимиты и квота | **Любой загружаемый файл** (шаблон DOCX или каждое приложение): **не более 10 МБ**. **Суммарная квота хранения на тенант** для артефактов модуля BL-18 (версии шаблонов, сохранённые пакеты выгрузки по политике ретенции, служебные копии вложений, связанные с недавними заданиями): **1 ГБ** по умолчанию (значение — продуктовый дефолт, допускается настройка на стороне развёртывания). Превышение квоты — **отказ в новой загрузке** с понятным сообщением до освобождения места или повышения квоты (админ тенанта). Временные буферы обработки (распаковка, антивирус) учитываются в реализации так, чтобы не обходить квоту бесконтрольно (TTL и очистка). Детали — §2.1. |

### 2.1 Детализация лимитов и квоты

- **10 МБ** — жёсткий потолок на **один** файл при загрузке (шаблон или приложение); до **5** приложений + один шаблон в рамках одной операции — каждый файл проверяется отдельно.
- **1 ГБ на тенант** — ориентир для **постоянного и кэшируемого** хранилища фичи; не включает произвольно долгий «мусор» без TTL (в задачах разработки зафиксировать политику удаления черновиков и временных файлов).
- При **нуле приложений** ZIP-пакет в MVP **всё равно формируется** и содержит **только** `letter.docx` (единый файл в архиве).

## 3. Объём MVP vs последующие версии

### 3.1 Обязательно в MVP

1. **Привязка к AI PMO:** аутентификация/контекст тенанта и пользователя; операции видны в продуктовом контуре AI PMO.
2. **Загрузка и версионирование шаблона:** сохранение DOCX-шаблона с метаданными (название, организация/подразделение — по политике продукта).
3. **Разметка шаблона:** в шаблоне фиксированные **плейсхолдеры** для подписи и реквизитов подписанта, например `{{SIGNATORY_NAME}}`, `{{SIGNATORY_TITLE}}` — **никогда не заполняются автоматически** из профиля или ИИ; пользователь дописывает в Word вручную или через отдельное явное действие «вставить из профиля» **вне** MVP, если будет запланировано.
4. **Ввод сути:** одно поле (или несколько логических блоков UI), **только русский язык**; валидация «основной язык текста — русский» по эвристике (достаточно для MVP).
5. **Генерация текста письма:** модель формирует **тему (при необходимости)**, **обращение**, **тело**, **заключительная фраза**, блок **«Приложения: …»** (список по загруженным файлам) — в структуре, согласованной с полями шаблона.
6. **Сборка DOCX:** серверная подстановка в шаблон (**docxtpl** / аналог): бланк остаётся на сервере, в LLM **не уходит**.
7. **Приложения (файлы):** приём до 5 файлов, антивирус, лимит **10 МБ** на файл (см. §2.1); в итоговом DOCX — **упоминание и перечень** приложений; **встраивание бинарников приложений в итоговый DOCX** в MVP **опционально** (основная передача оригиналов пользователю — через ZIP, п. 8).
8. **Вторая выгрузка (обязательно в MVP):** после успешной сборки пользователь скачивает **ZIP-архив**, в корне которого: **`letter.docx`** (собранное письмо, то же содержимое, что и в отдельной выгрузке DOCX) и **оригинальные файлы приложений** с **исходными именами и байтами** (без перекодирования). Коллизии имён в ZIP (два одинаковых имени) — разрешить в реализации суффиксом (`_2`) или запретить на этапе загрузки; зафиксировать в задачах.
9. **Предпросмотр / скачивание:** отдельное скачивание **DOCX письма** и скачивание **ZIP-пакета** (две кнопки или одна «Скачать пакет» + «Скачать только письмо» — на усмотрение UX, оба артефакта доступны).
10. **Журнал аудита** (см. §8), в т.ч. факт выдачи ZIP (без хранения бинарника в логе).

### 3.2 Вне MVP (бэклог после v1)

- **Согласование** (маршруты, статусы).
- **Версионирование** черновиков и сравнение версий.
- **Экспорт в почту** (SMTP / интеграция с почтовым клиентом).
- **Реестр исходящих** (учёт номеров, жёсткая нумерация, поиск).
- **Голосовой ввод (STT)**.
- **Автоподстановка** ФИО/должности из профиля (только после отдельного юридического/продуктового решения).
- **Полная** интеграция приложений как встроенные объекты в один DOCX без ограничений формата.

## 4. Стиль, тон и нормы

- **Источник правды по оформлению:** структура и стиль **заданы шаблоном** (поля, порядок реквизитов, отступы).
- **Источник правды по языку:** системный промпт и пост-правила генерации.
- **По умолчанию (MVP):** нормы **официально-делового письма на русском** в духе **ГОСТ Р 7.0.97-2016** (где применимо к структуре: адресат, исходящий контекст, ссылки на приложения, подпись — как плейсхолдеры). Точное юридическое соответствие ГОСТ не заявлять в UI; формулировка для пользователя: «официально-деловой стиль, ориентир — российская служебная переписка».
- Модель **не видит** бланк; инструкции по стилю — в промпте + опционально **краткий** «паспорт шаблона» (2–5 предложений: тип организации, обращение «Уважаемый…» / «Уважаемые…»), задаётся **вручную** при загрузке шаблона или извлекается **локальными эвристиками без отправки DOCX в LLM** (например, только название шаблона и пользовательские теги — явно в ТЗ реализации).

## 5. Политика подписанта и персональные данные

- **Запрещено:** автоматическая подстановка **ФИО** и **должности** подписанта моделью или бэкендом без отдельного явного сценария (в MVP такого сценария **нет**).
- **Обязательно:** в DOCX остаются **плейсхолдеры** (`{{SIGNATORY_NAME}}`, `{{SIGNATORY_TITLE}}` или эквивалент, согласованный с библиотекой шаблонов).
- В промпт явно: «не выдумывай ФИО, должности, телефоны, email; если не хватает данных — используй нейтральные формулировки или оставь указание пользователю в скобках».
- **ПДн в теле письма:** пользователь может ввести ПДн контрагентов; в MVP — **информирование** и ссылка на политику обработки; техминимизация — не логировать полный текст в аудите (§8).

## 6. Данные, разрешённые для передачи в LLM (MVP)

**В LLM передаётся только:**

1. **Текст сути письма** (RU).
2. **Краткие метаданные запроса:** идентификатор шаблона (uuid), **человекочитаемое имя шаблона**, опционально **паспорт стиля** (короткий текст, не содержимое бланка).
3. **Список приложений:** только **имена файлов** и **типы**; опционально для MVP флаг «**учитывать содержание**» — если включён, в LLM может передаваться **локально извлечённый plaintext** из PDF/DOCX/XLSX с **жёстким лимитом** символов и **без** восстановления макета бланка. Если флаг выключен — только перечень.

**В LLM не передаётся:**

- Бинарный/текстовый **DOCX шаблона** и любые его фрагменты, извлечённые из шаблона для «обучения» модели.
- Логотипы и сканы как изображения из шаблона.

**Трансграница (MVP):** при вызове зарубежного API — в пользовательском соглашении/чекбоксе явно: категории уходящих данных, цель, срок, отсутствие использования для обучения (если провайдер это гарантирует договором).

## 7. Cursor SDK — целесообразность

| Критерий | Рекомендация |
|----------|----------------|
| Основной путь генерации в MVP | **Прямой вызов LLM HTTP API** из бэкенда РФ (минимальная задержка, простой контракт JSON in/out). |
| Cursor SDK (`@cursor/sdk`) | **Опционально**, если нужны: многошаговая **полировка** текста с инструментами, **MCP** к корпоративным регламентам, или **внутренний** сценарий для команды продукта. Тогда отдельный **TypeScript worker** вызывается из оркестратора; **шаблон по-прежнему не передаётся** — только разрешённые поля §6. |
| Риски SDK | Агентский рантайм, облако Cursor, дополнительная **латентность** и **комплаенс**; для массового пользовательского MVP **не делать обязательной зависимостью**. |

**Итог для спеки:** MVP = **прямой LLM**; в архитектурной схеме заложить **слот** «Text generation provider» с возможной реализацией через Cursor SDK во **v1.1+**.

## 8. Журнал аудита (обязательные поля события)

Минимальный набор полей на событие `letter.generate` (или аналог):

- `timestamp` (UTC+MSK отображение в UI)
- `tenant_id`, `project_id` (если есть в AI PMO), `user_id`
- `template_id`, `template_version`
- `request_id`
- `model_id` / `provider` (без секретов)
- `attachment_count`, `attachment_names` (или hashes)
- `zip_issued` (boolean) — пользователю выдан ZIP-пакет; опционально `zip_bytes` hash (не сам архив)
- **Не хранить** в открытом виде: полный текст сути и полный сгенерированный текст (MVP); допускается хранение **хэша** или отключение content-log по умолчанию. Расширяемо по политике ИБ.

## 9. Контракт API (логический, MVP)

**Запрос:**

- `template_docx` (multipart) — при создании/обновлении шаблона
- `gist_text` (string, RU)
- `attachments[]` (0–5, `.xlsx` | `.docx` | `.pdf`)
- `include_attachment_content_in_llm` (boolean, default `false`)

**Ответ:**

- `result_docx` (binary) — письмо для прямого открытия в Word
- `result_zip` (binary) — архив: **`letter.docx`** + **оригиналы** приложений (0–5 файлов); при отсутствии приложений — архив только с `letter.docx`
- `audit_id`

**Детализация REST (принято для prod):** см. `docs/ADR-BL-18-02-production-decisions.md` §10 — префикс `/api/tenants/:tenantId/...`, отдельные endpoints для шаблонов и генерации, ответ с URL скачивания или `202` при больших файлах.

## 10. Ошибки и границы

- Файл **> 10 МБ** или превышение **квоты тенанта 1 ГБ** (артефакты модуля) → понятная ошибка с указанием лимита / оставшегося объёма (если доступно).
- Невалидный шаблон (нет обязательных плейсхолдеров тела письма) → отказ с указанием **чеклиста** для администратора шаблонов.
- Сбой LLM → повтор с идемпотентностью по `request_id`; пользователю — статус и запись в аудите.

## 11. Критерии приёмки MVP (выжимка)

1. Пользователь с контекстом AI PMO загружает DOCX-шаблон (**≤10 МБ**), при необходимости до 5 вложений (**каждое ≤10 МБ**), вводит русскую суть и скачивает **DOCX письма** и **ZIP-пакет** (состав ZIP — пункт 6 ниже); хранилище тенанта укладывается в **квоту 1 ГБ** для модуля BL-18.
2. **Доказуемо** (логирование на границе провайдера + код): **ни один запрос к LLM не содержит** тело шаблона DOCX.
3. В итоговом файле **ФИО и должность** подписанта — только плейсхолдеры, не заполненные автоматически.
4. До 5 вложений допустимых форматов; в письме отражены в перечне приложений.
5. Аудит содержит пользователя, шаблон, время, провайдера модели и факт выдачи ZIP (§8).
6. Пользователь получает **ZIP**: внутри **`letter.docx`** и **оригиналы** всех загруженных приложений с исходными именами; при отсутствии приложений — ZIP только с `letter.docx`.
7. Вне MVP не требуются: согласование, версии, почта, реестр исходящих.

| Тема | Документ |

**Кратко:**

- **DOCX:** `docxtemplater` (Node).
- **ZIP-коллизии:** суффикс `_2` в архиве.
- **Ретенция:** temp 24 ч; артефакты скачивания 7 суток (если persist); аудит 13 мес.
- **Плейсхолдеры:** обязательный чеклист в ADR-BL-18-02 §5.1.

Спека **достаточна для продуктивного развёртывания** вместе с указанными ADR и runbook.

## 13. Модель тенанта (выжимка для разработчиков)

Полное сравнение **варианта A** (мультитенант) и **варианта B** (single-tenant) — в `docs/ADR-BL-18-01-tenant-model.md`.

| | A — мультитенант | B — single-tenant |
|---|------------------|-------------------|
| **Квота 1 ГБ** | На каждую организацию | На весь инстанс (одна «организация») |
| **Изоляция** | Да | Нет |
| **Для публичного SaaS** | Да (рекомендуется) | Нет |
| **Схема `tenant_id` в аудите** | Реальный UUID | Константа `DEFAULT_TENANT_ID` |

**Принято для AI PMO prod:** **A₀** — схема A с одним seed-тенантом; при росте добавляются тенанты без смены контракта аудита.
