## 0. Контекст и место в продукте

BL-36 — **ingestion-ядро волны 2** и критический путь: `BL-36 → BL-50/BL-39 → BL-38/BL-41 → BL-11`. Все sense-making фичи (Commitment Tracking, Early Warning, Decision Log, Health Score) потребляют поток сигналов, который производит BL-36. BL-52 (Email-надзор) архитектурно переиспользует pipeline и объектную модель BL-36.

**Боль:** решения и договорённости тонут в потоке переписки; документы проекта расходятся с реальностью; РП вручную собирает новости по проекту.

**Стратегическая рамка (20.09.2026):** канал — место действия, реестр — система записи (audit view). Действие (подтверждение/отклонение) происходит в Telegram через кнопки; реестр не обязателен для продвижения работы.

---

## 1. Цель и результат

**Цель:** бот присутствует в рабочих TG-чатах проекта, фильтрует шум, извлекает сигналы (поручения, решения, договорённости, риски) и превращает их в **предложения** для РП с кликабельными ссылками на исходные сообщения.

**Результат MVP:**
1. Бот-наблюдатель собирает сообщения из подключённых чатов (Bot API, бот — админ чата).
2. LLM-пайплайн выделяет сигналы и формирует предложения (proposal) с обоснованием «Почему предлагает».
3. РП подтверждает/правит/отклоняет предложения кнопками в Telegram; подтверждённые поручения пишутся в реестр BL-6, все записи — в Supabase.
4. Ежедневный дайджест новостей проекта в TG.
5. Предложения видны в веб-воркспейсе (очередь «Входящие предложения») — через Supabase.

## 3. Объектная модель (тонкий срез BL-13)

```
Project (проект)
 └─ Channel (подключённый TG-чат: chat_id, title, статус подключения)
     └─ Message (сырое сообщение: msg_id, автор, текст, дата, reply_to, ссылка)
         └─ Signal (выделенный факт: тип, суть, ссылки на Message[])
             └─ Proposal (предложение в реестр: целевой реестр, payload,
                          обоснование, статус, diff для изменений)
                 └─ RegistryRecord (подтверждённая запись: BL-6 / Supabase)
Participant (участник проекта: ФИО, TG-login, компания, роль; связь с «Контактами» BL-6)
```

**Типы сигналов (MVP):** `assignment` (поручение), `decision` (решение/договорённость), `risk` (риск), `news` (новость для дайджеста). Типизация рисков — не делаем (решение 17.09).

**Статусы Proposal:** `pending` → `confirmed` | `edited_confirmed` | `rejected` | `merged` (дедупликация) | `expired`.

**Кликабельный источник:** ссылка вида `https://t.me/c/<chat_id>/<msg_id>` для супергрупп; хранится в Signal и Proposal (обязательное поле).

## 4. Архитектура

```
TG-чаты проекта
   │ (Bot API getUpdates / webhook, бот — админ)
   ▼
listener.py ──→ buffer (Supabase: bl36_messages)
   │                ▲ фильтр шума (эвристики: длина, стикеры, флуд)
   ▼                │
scheduler (systemd timer / цикл) ──→ sense.py
   │  батч сообщений → LLM kimi-k2.6 (thinking вкл) → JSON сигналов
   ▼
proposals: bl36_signals + bl36_proposals (Supabase)
   │
   ├─→ bot.py: карточка предложения РП в TG (✓ / ✕ / ✎→✓)
   │        ✓ → запись: поручение → Google Sheets BL-6 (API task_manager),
   │             прочее → Supabase; статус proposal → confirmed
   │
   ├─→ веб-воркспейс BL-35: очередь «Входящие предложения» (читает Supabase)
   │
   └─→ digest.py: ежедневный дайджест новостей (по сигналам типа news +
        подтверждённым записям), механика last_digest.json из BL-6
```

**Компоненты (код, `bl36-tg-monitor/`):** `scripts/` — listener, sense (LLM), proposals, digest, config, db (Supabase client), sheets_bridge (запись в BL-6). Отдельный бот, отдельный systemd-сервис `bl36-tg-monitor.service`. Деплой-цикл как у BL-6/BL-28: `py_compile → scp → systemctl restart`.

## 5. Модель доверия и UX (требования ревью 20.09.2026)

1. **Единая модель доверия:** «Входящие предложения» (очередь) → подтверждённые записи. Авто-записи не попадают в реестр как полноправные.
2. **Кликабельный источник** у каждого предложения: «TG · чат АСУП-интеграция · 18.09 14:32 →».
3. **Бейдж канала:** TG / почта / MAX / чат WS (в MVP — TG).
4. **Права:** утверждает только РП. Кнопки ✓/✕ для остальных недоступны (проверка по `owner_id`/ролям в конфиге).
5. **Счётчик «ожидают решения»** — в боте (команда/кнопка «📥 Предложения (N)») и в веб-воркспейсе.
6. **Блок «Почему предлагает»** — обязателен в карточке предложения: обоснование + ожидаемый эффект + цитаты из сообщений.
7. **Diff-паттерн:** предложение может изменять существующую запись («срок: 18.09 → 22.09») с ✓/✕ по полю.
8. **Дедупликация:** два предложения об одном факте → «похоже на P-01 (совпадение 92 %) — объединить?». Символьная проверка + семантическая через LLM (опыт `find_semantic_duplicate` из BL-6).
9. **Третье действие:** «✎ Изменить и принять» — РП правит фразой перед принятием (LLM-режим как в BL-6).

## 6. Функциональные требования (MVP)

### 6.1 Подключение чата
- Админ добавляет бота в TG-чат и выдаёт права администратора (privacy off).
- Бот фиксирует подключение: `chat_id`, название, привязка к проекту; подтверждение РП в личку.
- Команда `/status` — список подключённых чатов, счётчики сообщений/сигналов.

### 6.2 Сбор и фильтрация
- Listener сохраняет текстовые сообщения (и подписи к файлам) в `bl36_messages`: chat_id, msg_id, автор (TG-login/имя), текст, reply_to, дата, ссылка.
- Фильтр шума до LLM: стикеры/эмодзи-only, сообщения < 25 знаков без reply (как MIN_MATERIAL_CHARS в BL-28), служебные события.
- Сообщения ботов игнорируются (кроме белого списка — напр. дайджесты BL-6 при явной настройке).

### 6.3 Sense-making (LLM)
- Расписание: каждые 30 мин (настраивается) + по команде; батч новых сообщений по чату.
- Модель: kimi-k2.6, thinking включён, max_tokens=8000, timeout=120 (как совет дайджеста BL-6). Rate limit: последовательные вызовы, backoff при 429 (аккаунт общий с BL-6/BL-1).
- Промпт возвращает JSON-массив сигналов: `{type, summary, assignee?, due?, rationale, quote_msg_ids[], confidence}`.
- Каждый сигнал обязан ссылаться на ≥1 сообщение; сигнал без источника отбрасывается.
- Маппинг участников: TG-login/имя → Participant (ФИО, компания) через «Контакты» BL-6 (нечёткий матчинг `normalize_assignee_format`).

### 6.4 Предложения и подтверждение
- Сигнал → карточка предложения РП в личку (или чат РП): тип, суть, «Почему предлагает», цитата-источник со ссылкой, кнопки ✓ / ✕ / ✎.
- ✓ по поручению → запись в реестр BL-6 через `task_manager` (статус «В работе», приоритет по умолчанию 2, контрагент из «Контактов» — как в BL-6); прочие типы → таблицы Supabase (`bl36_decisions`, `bl36_risks`).
- ✎ → LLM-режим правки фразой (переиспользовать паттерн «Редактировать» BL-6), затем повторный предпросмотр.
- ✕ → статус `rejected` + опциональный комментарий (обучающий сигнал для будущего BL-«самоулучшение»).
- Изменение существующего поручения: proposal типа `update` с diff полей; ✓ → команда BL-6 («срок #N …», «приоритет #N …»).

### 6.5 Дайджест
- Ежедневно (время настраивается, дефолт 9:17 МСК — рядом с дайджестом BL-6): новости проекта (сигналы `news`), принятые решения, новые поручения, риски за сутки, со ссылками на источники.
- Удаление предыдущего дайджеста — механика `last_digest.json` из BL-6; авто-миграция chat_id (группа → супергруппа) — паттерн `_migrate_chat_id`.
- Переключатель авто-дайджеста + кнопка «Дайджест» по запросу.

### 6.6 Веб-воркспейс (интеграция BL-35)
- Supabase-таблицы предложений читаются воркспейсом: очередь «Входящие предложения» с бейджами канала, счётчиками в меню, блоком «Почему предлагает».
- Действия из веба в MVP — только просмотр и комментарии (утверждение — в TG, канал = место действия). Полные кнопки в вебе — фаза 2.

## 9. Ключевые сценарии

1. **Подключение:** РП добавляет бота в чат проекта → бот просит права админа → чат появляется в `/status` → сбор начат.
2. **Поручение из переписки:** «Даша, пришли протокол до пт» → сигнал → карточка РП: «Поручение: Давыдова Д., протокол встречи, срок 26.09. Почему предлагает: прямая просьба с адресатом и сроком (цитата →)». ✓ → строка в реестре BL-6.
3. **Решение:** «Договорились: приёмка без ЭП, подписываем сканами» → предложение в журнал решений → ✓ → `bl36_decisions` (в будущем — BL-40).
4. **Изменение:** «Переносим демо на вторник» → proposal-update: «Поручение №4, срок: 22.09 → 23.09» → ✓ по полю → команда в BL-6.
5. **Дедупликация:** тот же факт в двух чатах → «похоже на P-01 (92 %) — объединить?».
6. **Дайджест:** в 9:17 МСК РП получает новости проекта со ссылками; воркспейс показывает счётчик «Поручения ●2».

## 10. Вне MVP (явно)

- Email-сбор (BL-52 — отдельная фича, переиспользует pipeline), MAX.
- Runtime-типизация рисков; авто-актуализация ТЗ/плана/RACI (предложения по документам — фаза 2).
- Полные действия ✓/✕ из веб-воркспейса; NLP-тональность (BL-7 Stakeholder Pulse).
- Multi-project UI в боте (модель поддерживает, UX — один активный проект).

## 11. Критерии приёмки MVP

1. Бот-админ собирает сообщения ≥ 2 тестовых чатов, шум отфильтрован.
2. На контрольном диалоге (фикстура) извлекаются поручение/решение/риск с корректными ссылками на источники — recall по разметке ≥ 80 %, без выдуманных фактов.
3. Подтверждённое поручение появляется в Google Sheet BL-6 с корректным ответственным (формат «Фамилия И.») и контрагентом.
4. Отклонённые предложения не попадают в реестры; статусы видны в `/status`.
5. Дайджест приходит по расписанию, прошлая версия удаляется.
6. Предложения читаются из Supabase веб-воркспейсом (проверка SQL-запросом).
7. Сервис переживает restart без потери неподтверждённых предложений (персистентность в Supabase).

## 13. Деплой и операции

- Сервер Timeweb (`root@195.133.14.151`): `/opt/bl36-tg-monitor/`, сервис `bl36-tg-monitor.service`, лог `/var/log/bl36-tg-monitor.log`.
- Конфиги (не в репо): `.credentials/` — telegram.json (token, owner_id, admin_ids), kimi.json, supabase.json, config.json (чаты, расписание, лимиты).

## 14. Данные и конфиденциальность

- Бот хранит содержимое рабочих чатов — мониторинг коммуникаций сотрудников (ТК РФ ст. 86–88, аналогично выводу по BL-6): для пилотов нужны DPA и локальные нормативные акты у заказчика; в онбординге — уведомление участников чата о присутствии бота.
- Сырые сообщения: TTL хранения 90 дней (настраивается), далее удаление; сигналы и предложения хранятся бессрочно.
- Секреты только в `.credentials/` на сервере; в git не коммитятся.

## 15. Открытые вопросы

1. Имя/username бота (напр. @PMO_watch_bot) — создать через BotFather перед фазой 1.
2. Один проект на инстанс или сразу мульти-проект в конфиге (модель поддерживает оба).
3. Порог `confidence` для авто-показа предложения (дефолт: показывать всё ≥ 0.5).
4. Нужна ли реакция-ручка в чате (напр. 🔖 reply-метка «в поручения») как ручной источник сигналов.
5. Точное расписание sense-making: 30 мин vs накопление ≥ N сообщений.
