# BL-50 · Commitment Tracking — автовыделение обязательств из переписки (развитие BL-6)

**Статус:** v1.0 — реализовано и проверено изолированно 10.11.2026, GitHub `ca4b0bd`; реальный пилот и production deployment не выполнялись.

**Основания:** карточка BL-50 в Notion, Product Contract v1, SPEC-P0, BL-36, BL-40, BL-41, BL-42, BL-48, BL-54.  
**Граница:** один проект. Поручение и изменение срока выполняются только после подтверждения РП.

## 1. Цель

Автоматически выявлять обязательства в переписке, предлагать РП зафиксировать или изменить их и сохранять проверяемый жизненный цикл:

`сигнал → кандидат → подтверждение/правка/отклонение/merge → поручение → результат → исход для BL-48/BL-55`.

Система не создаёт поручение из обычного обсуждения и не считает факт генерации ценностью.

## 2. Инварианты

1. Создание нового поручения и изменение существующего срока выполняются только РП.
2. Каждый кандидат имеет источник, проект, автора, ответственного, срок, confidence и версию доказательств.
3. Отклонение требует причину: `not_commitment`, `already_done`, `wont_do`.
4. Отклонённый кандидат не предлагается повторно по тем же доказательствам; возврат возможен только по новому сообщению.
5. Совпадение ≥ 0.92 предлагает merge вместо нового поручения.
6. Изменение срока существующего поручения показывает `было → стало`, сохраняет прежнее значение и не создаёт дубль Task.
7. Повтор webhook/callback не создаёт дубли кандидата, решения, поручения, изменения срока или результата.
8. Выполнение само по себе не доказывает эффект; оценка эффекта остаётся в BL-48.
9. Рабочие чаты read-only. Персональные предложения и напоминания — только в разрешённые личные чаты.
10. Все исходы доступны BL-48 и BL-55 без персональных chat/user IDs в evidence.

## 3. Объектная модель

### CommitmentCandidate

- `id`, `projectId`, `signalId`, `decisionId`, `taskId`, `existingTaskId`.
- `title`, `owner`, `due`, `confidence`, `changeType`: `create` | `update`.
- `status`: `pending`, `pending_merge`, `accepted`, `edited`, `rejected`, `merged`, `ignored`, `completed`.
- `rejectionReason`: `not_commitment` | `already_done` | `wont_do` | null.
- `evidenceVersion`, `evidenceHash`, `editDistance`.
- `createdAt`, `updatedAt`, `decidedAt`, `completedAt`.

### CommitmentOutcome

Канонический результат, а не только текст Task.result:

- `id`, `projectId`, `taskId`, `decisionId`.
- `outcome`: `on_time` | `late` | `ignored` | `unknown`.
- `resultText`, `completedAt`, `source`, `sourceId`.
- `expectedEffect`, `effectAssessment` при наличии из BL-48.
- `recordedByUserId`, `recordedByName`, `recordedByRole`.
- `createdAt`, `updatedAt`.

Одна активная запись на Task. Повторное подтверждение обновляет только допустимые поля и не создаёт второй результат или audit event.

## 4. Выделение обязательств

1. Анализ сообщения возвращает `isCommitment`, `title`, `owner`, `due`, `changeType`, `existingTaskId`, `confidence`.
2. `isRisk` и `isCommitment` — разные решения классификатора. Рисковый контур сохраняет приоритет P0 и не дублируется.
3. Пустые/неизвестные owner/due допускаются только с честным `—`, но подтверждение поручения требует валидный срок.
4. Прошедшая дата не создаёт корректное новое бизнес-поручение; она возвращается на проверку РП без автоматического принятия.
5. `changeType=update` допускается только для существующей Task того же проекта. Иначе кандидат получает ошибку сопоставления, а не новый Task.
6. AI failure не создаёт кандидат, Risk, Decision или Task и показывает честную ошибку без слепого retry.

## 5. Подтверждение, правка, отклонение и merge

- Accept использует существующий атомарный `decideProposalRecord`: Decision + один Task + audit.
- Edit использует существующий preview → Accept с версией, diff и edit distance.
- Reject открывает выбор причины; Decision не закрывается до выбора причины.
- Accept `update` меняет только `tasks.due` и создаёт `commitment.rescheduled` с old/new, версией и RP attribution.
- Merge связывает кандидат с существующей Task, помечает `merged` и не создаёт Decision/Task.
- `ignored` используется для повторного отклонённого кандидата по тем же доказательствам. Новое доказательство создаёт новую evidenceVersion и допускает отдельный кандидат.

## 6. Результат и исходы

1. «Выполнено» атомарно закрывает Task и создаёт/обновляет CommitmentOutcome.
2. `on_time` при `completedAt <= распознанный срок`, иначе `late`.
3. «Не выполнено» оставляет Task открытым и не создаёт завершённый Outcome.
4. Игнорирование/просрочка без результата получает `ignored` только по отдельному правилу жизненного цикла, а не автоматически в день срока.
5. Неизвестный результат внешней доставки не меняет Outcome.
6. Audit события: `commitment.proposed`, `commitment.accepted`, `commitment.edited`, `commitment.rejected`, `commitment.merged`, `commitment.rescheduled`, `commitment.outcome.recorded`.
7. В metadata сохраняются source, evidenceVersion, rejectionReason, editDistance, old/new due, outcome и effectAssessment при наличии.

## 7. Дайджест, SLA и BL-35

- Просроченные обязательства включаются в раздел «Риск — что мешает» по существующим правилам BL-54, без новых выдуманных рисков.
- Напоминания и эскалации используют BL-42 и только разрешённые личные получатели.
- BL-35 показывает Candidate, источник, статус, rejectionReason, old/new due, editDistance и CommitmentOutcome.
- BL-48 получает Outcome и связанный EffectAssessment без дублирования ручной оценки РП.
- BL-55 получает acceptance/reject/edit/merge/reschedule/outcome события с версиями и причинами.

## 8. Критерии изолированной приёмки

- [ ] Обычное обсуждение не создаёт кандидат.
- [ ] Валидное обязательство создаёт один Candidate и RP DM proposal.
- [ ] Accept создаёт атомарно один Decision и один Task.
- [ ] Edit сохраняет версию, diff и editDistance.
- [ ] Reject требует причину и не создаёт Task.
- [ ] Повтор по тем же доказательствам получает `ignored`; новое доказательство допускает новую версию.
- [ ] Сходство ≥ 0.92 предлагает merge вместо нового Task.
- [ ] `update` меняет существующий срок с old/new и не создаёт второй Task.
- [ ] Несуществующий/чужой existingTaskId отклоняется.
- [ ] Повтор callback/restart не дублирует записи и audit.
- [ ] `on_time` и `late` вычисляются корректно; `unknown` не выдаётся за успех.
- [ ] PMO/аудитор/C-level/member не могут подтверждать, отклонять или менять срок.
- [ ] Просроченные обязательства видны в дайджесте и BL-35.
- [ ] BL-48/BL-55 получают согласованные исходы и версии.
- [ ] Прежние P0/BL-48 regressions, unit, typecheck и build проходят.

## 9. Реальная приёмка

1. Только по согласованному сценарию использовать один реальный сигнал обязательства, без изменения webhook/gateway.
2. Проверить Accept, Reject с причиной, Edit и merge/update на изолированных копиях либо согласованных сущностях.
3. Проверить фактический срок, напоминание ответственному и дайджест без групповых исходящих.
4. Проверить CommitmentOutcome, BL-48 и данные для BL-55 после restart.
5. Sanitized evidence не содержит chat/user IDs, тексты переписки или персональные данные сверх разрешённого сценария.

## 10. Не входит в срез

- Портфельная аналитика и межпроектное обучение.
- Автоматическое принятие обязательств или изменение срока без РП.
- Автоматическое дообучение модели и автономная смена логики — это BL-55 с человеческим утверждением.
- Email и MAX как новые каналы.
- Полный persisted outgoing queue, dead-letter и monitoring — отдельная спецификация.
