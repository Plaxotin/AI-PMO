## 1. Цель и результат

Сервис фиксирует поручения из **Telegram** (текст и голос), ведёт **единый реестр по проекту** с минимальными обязательными полями: **описание, срок, ответственный**. При неполных данных сервис задаёт уточняющие вопросы. За настроенное время до дедлайна отправляет уведомление в тот же Telegram-канал. Актуальная версия реестра публикуется в открытый доступ с упором на доступность из РФ. Поддерживаются выгрузка и ручные корректировки с повторной публикацией.

**Убийственный сценарий для рынка РФ:** пользователь отправляет запись летучки или созвона (аудио **или видео**) в Telegram-бота либо загружает файл напрямую через веб-интерфейс AI PMO — в приложении появляется структурированный список поручений с описаниями, сроками и ответственными. Это полноценный UX продукта, а не только публичный снапшот реестра.

## 3. Объём MVP

### 3.1 Обязательно в MVP

1. **Модель поручения:** `id`, `project_id`, `title`, `description` (опц.), `status` (enum: `draft` | `open` | `done` | `cancelled`), `due_at` (опц.), `assignee` (Telegram @username / user_id / отображаемое имя), `source` (`manual` | `import` | `webhook` | `web_upload`), `created_at`, `updated_at`, `history`, `version` (с BL1-1).
2. **Приём из Telegram:** текст, голосовые и видеосообщения, медиафайлы из привязанного канала / супергруппы; webhook с верификацией токена.
3. **STT для аудио и видео:** скачать файл (voice / audio / video) → извлечь аудиодорожку (для видео) → **SaluteSpeech** → нормализация текста → тот же pipeline, что и текст. Медиафайл **не сохраняется** — обрабатывается только в памяти/temp и удаляется сразу после транскрипции.
4. **Ключевой сценарий «запись с мероприятия»:** файл летучки/созвона (**аудио или видео**, переданный боту в Telegram **или загруженный через веб-интерфейс AI PMO**) → STT + LLM-разбиение → структурированный список поручений в веб-UI AI PMO с подтверждением.
5. **Уточняющие вопросы:** диалог в ЛС с ботом или в треде; до заполнения трёх обязательных полей запись остаётся черновиком (`draft`).
6. **Уведомления в канал:** сообщение с описанием, сроком, ответственным и ссылкой на публичную строку реестра; антидубли.
7. **Публичный реестр:** статический снапшот JSON + HTML-таблица на RU-friendly CDN; версионирование `updated_at` / ETag.
8. **CRUD в веб-UI AI PMO:** список, карточка, форма создания/редактирования; фильтры по статусу, сроку, ответственному.
9. **Выгрузка и ручные правки:** экспорт CSV/XLSX; импорт с валидацией и отчётом об ошибках; optimistic locking по `version`.
10. **Журнал событий:** кто и когда создал / изменил / закрыл поручение; смена `status` и ключевых полей (`title`, `due_at`, `assignee`) — в `assignment_status_events` с `event_type` (`status_change` | `field_change` | …). См. `docs/specs/BL6_PRODUCT_DECISIONS.md`.

### 3.2 Вне первой итерации (бэклог)

- Несколько каналов и матрица ролей; SSO / корпоративный LDAP.
- Другие мессенджеры (Slack, e-mail).
- Автоматическое определение ответственного из LDAP/HR по @username.
- Сложная дедупликация поручений с LLM-сравнением семантики.
- Мобильное приложение / PWA.
- Полная матрица мессенджеров, двусторонняя синхронизация переписки, юридическое DLP/архивирование чатов, внешние таск-трекеры (**BL-6+**).
- Мульти-канальный ввод, дедупликация на LLM, синхронизация статусов с перепиской — после стабильного реестра и одного канала.

### 3.3 Вне MVP (явно не входит)

- Публичный REST API реестра для третьих сторон (как отдельный продукт).
- Произвольная двусторонняя синхронизация статусов с мессенджерами.
- Юридически полное DLP и архивирование переписки.

### 3.4 Принципы и риски

**Принципы:** извлечение сущностей из свободного текста **не заменяет** явные поля в БД после подтверждения; PII и хранение сырья — по политике проекта (ретенция, маскирование в логах).

**Риски:** качество STT/LLM, доступ бота к каналу, согласование @username vs ФИО, спам/дубликаты вебхуков — идемпотентность, rate limit, пометка «возможный дубль» в UI.

## 4. Функциональные требования

### 4.1 Ввод: Telegram и веб-загрузка

Поддерживается **два канала подачи** записей мероприятий:

**Telegram (webhook):**

- Сообщения из привязанного канала/супергруппы обрабатываются через **webhook** (Telegram Bot API).
- **Текст:** извлечение `description`, `due_at`, `assignee` — эвристики + LLM slot-filling при необходимости.
- **Голос (voice / audio):** скачать файл временно → **SaluteSpeech** STT → удалить файл → обработать транскрипт как текст.
- **Видео (video / video_note):** скачать файл временно → извлечь аудиодорожку (ffmpeg) → **SaluteSpeech** STT → удалить файл → обработать транскрипт как текст.

**Веб-загрузка (web upload) в AI PMO:**

- На странице проекта — форма загрузки файла с мероприятия: принимаются форматы **аудио** (`.mp3`, `.m4a`, `.ogg`, `.wav`, `.opus`) и **видео** (`.mp4`, `.mov`, `.webm`, `.mkv`).
- Пользователь опционально указывает контекст: название мероприятия, дату, участников (помогает LLM точнее расставить ответственных).
- Pipeline: загруженный файл → **SaluteSpeech** STT → файл немедленно удаляется с сервера → LLM-разбиение на черновики поручений → экран подтверждения в UI → пользователь подтверждает / редактирует / отклоняет каждый черновик.
- Лимит файла: **≤ 500 МБ** (длинные записи совещаний); для файлов > 25 МБ — серверная обработка асинхронно, статус через polling или SSE.
- **Медиафайл не хранится** в БД или файловом хранилище AI PMO — оригинал остаётся только в Telegram-канале или на устройстве пользователя.

**Общее:**

- **Ключевой сценарий «запись с мероприятия»:** файл летучки/созвона (аудио или видео) передаётся в бота **или** загружается через веб → в AI PMO появляется структурированный список поручений.
- Минимальная запись **не создаётся в «боевом» реестре**, пока не заполнены три обязательных поля. До этого — черновик и сессия уточнений.

### 4.2 Уточняющие вопросы

- Диалог — **тред под исходным сообщением** (зафиксировано как дефолт для пилота). Личка с ботом — опция для последующих версий.
- Максимум раундов уточнений (например 3); таймаут черновика (например 24 ч) с автоотменой.
- После заполнения минимума — финализировать `Assignment`, статус меняется с `draft` на `open`; бот отправляет краткое подтверждение.
- LLM задаёт не более 1–3 вопросов за раунд, не переспрашивает поля с высоким confidence.

### 4.3 Уведомления в канал

- За N часов/дней **и/или** в день дедлайна — сообщение в тот же Telegram-канал.
- Антидубли: лог напоминаний `ReminderLog` по `(assignment_id, reminder_type)`.
- Текст уведомления: краткое описание, срок, ответственный, **ссылка на публичную строку реестра** (якорь/id).
- N (интервалы) и часовой пояс — конфигурируются на уровне проекта; можно отключить.

### 4.4 Публичный реестр (доступ из РФ)

- Публикация статического снапшота: **`registry.json`** + **`index.html`** (таблица, поиск на клиенте, без зарубежных runtime-зависимостей).
- Хостинг: **Yandex Object Storage** (зафиксировано) + Yandex CDN; международный mirror — опционально.
- Версионирование: `updated_at`, ETag для CDN-кэшей.
- Политика PII: в публичном слое только согласованные колонки.
- Обновление после каждой публикации ≤ 1–2 мин (или по кнопке «Опубликовать»).

### 4.5 Выгрузка и ручные правки

- **Экспорт:** CSV/XLSX полного реестра (или по проекту) с полем `updated_at`.
- **Импорт:** валидация, отчёт «принято / пропущено / конфликт», сопоставление по стабильному `id`; опционально diff-превью перед применением.
- **Ручные правки в UI:** форма редактирования с optimistic locking по `version`; доступ через **одноразовые signed links** (зафиксировано).
- После ручных правок — ре-публикация снапшота (автоматически или по кнопке).

## 6. Архитектура и Cursor-агенты

Детализированный план реализации — `docs/plans/ASSIGNMENTS_ADMIN_CURSOR_PLAN.md`. Ниже — сводка треков и фаз для работы в Cursor Cloud через агентов.

### Схема компонентов

```
Telegram (канал / личка)                Web-форма (AI PMO UI)
  │ текст / голос / видео                 │ аудио / видео файл (≤500 МБ)
  ▼                                       ▼
Bot Webhook ──────────────────► Media Ingest + STT + LLM slot-filling
                                          │
                                  ClarificationSession / Confirm UI
                                          │
                                    API + DB (Postgres)
                                ┌────────────────────────┐
                                │                        │
                      Scheduler (cron / outbox)    Public static generator
                      → напоминания в канал        → registry.json + HTML → CDN (РФ)
                                                   ↑
                                        Import / Export / Admin UI
```

### Cursor-агенты (треки)

| Агент | Выход | Критерий готовности |
|-------|-------|---------------------|
| **A — Контракты и данные** | Zod-типы, SQL-миграции, seed | Миграции накатываются; типы согласованы |
| **B — Telegram: приём текста и голоса** | Webhook handler, STT | Сообщение из тестового канала → черновик в БД |
| **C — LLM slot-filling и уточнения** | Модуль `clarify`; состояние `ClarificationSession` | E2e-тест: неполное сообщение → вопросы → финальная запись |
| **D — Напоминания** | Worker/cron, `ReminderLog`, шаблоны | Тестовая запись получает пост в канал ровно один раз на интервал |
| **E — Публичный реестр** | `registry.json` + `index.html` + скрипт деплоя CDN | URL открывается из РФ; обновление ≤ 2 мин |
| **F — Выгрузка и ручные правки** | Экспорт CSV/XLSX; импорт с diff | Round-trip: экспорт → правка → импорт → снапшот обновлён |
| **G — Наблюдаемость и безопасность** | Структурированные логи, rate limit, чеклист угроз | Повторная доставка webhook не создаёт дубль; секреты только в env |

### Порядок слияния

1. **A** (схема) — параллельно с черновиком OpenAPI.
2. **B** + **C** — после A.
3. **D** — после B + C (нужны финальные записи).
4. **E** — после A (можно параллельно B с мок-данными).
5. **F** — после A и желательно E (общий формат снапшота).
6. **G** — непрерывно, финальный проход перед пилотом.

## 7. Данные и конфиденциальность

**В LLM передаётся только:**

1. Нормализованный текст сообщения (после STT, без бинарных данных).
2. Текущий черновик поручения (только заполненные поля — для контекста уточнений).
3. Набор полей для извлечения (описание задачи slot-filling, без истории чата).

**В LLM не передаётся:**

- Полный лог переписки канала.
- Персональные данные, не относящиеся к конкретному поручению.
- Аудиофайл (передаётся только в STT-сервис).

**Публичный реестр:** только согласованные колонки; ответственный — @username или отображаемое имя по политике проекта. Никаких внутренних id пользователей, email, номеров телефонов.

**Хранение медиафайлов (решение зафиксировано):** AI PMO **не хранит** аудио- и видеофайлы. Файл обрабатывается только в оперативной памяти или tmp-директории и удаляется сразу после передачи транскрипта из SaluteSpeech. Оригинал сохраняется только в Telegram-канале (для файлов из Telegram) или на устройстве пользователя (для веб-загрузки). В БД и Yandex Object Storage медиафайлы не попадают.

## 9. Контракт API (логический, MVP)

### Реестр поручений

```
GET    /api/projects/:projectId/assignments          — список с фильтрами
POST   /api/projects/:projectId/assignments          — создать поручение
GET    /api/projects/:projectId/assignments/:id      — карточка
PATCH  /api/projects/:projectId/assignments/:id      — обновить
DELETE /api/projects/:projectId/assignments/:id      — отменить (soft delete)
```

Фильтры списка: `status`, `due_before`, `due_after`, `assignee` (**точное совпадение** с `assignee_label`), `source`, `page`, `per_page`.

Ответ: `{ data: Assignment[], meta: { total, page, per_page } }`.  
Версионирование схемы: заголовок `X-Api-Version` или query-параметр.

### Webhook Telegram

```
POST /api/telegram/webhook    — приём обновлений от Telegram Bot API
```

Верификация `X-Telegram-Bot-Api-Secret-Token`. Идемпотентный ключ: `chat_id` + `message_id`. Быстрый ответ 200 (обработка асинхронно).

### Веб-загрузка медиафайла (аудио / видео)

```
POST /api/projects/:projectId/media/ingest
     Content-Type: multipart/form-data
     Fields:
       file          — аудио (.mp3 .m4a .ogg .wav .opus) или видео (.mp4 .mov .webm .mkv), ≤ 500 МБ
       meeting_title — название мероприятия (опц.)
       meeting_date  — дата в ISO-8601 (опц.)
       participants  — JSON-массив имён/usernames участников (опц., подсказка для LLM)

GET  /api/projects/:projectId/media/ingest/:jobId   — статус обработки (pending|processing|done|failed)
GET  /api/projects/:projectId/media/ingest/:jobId/drafts — список черновиков после обработки
POST /api/projects/:projectId/media/ingest/:jobId/confirm
     Body: { accepted: [draftId, ...], rejected: [draftId, ...], overrides: { draftId: { ... } } }
     — подтвердить/отклонить черновики; принятые переходят в статус open
```

Для файлов > 25 МБ обработка асинхронна; статус через polling `GET …/ingest/:jobId` или Server-Sent Events.

Ответ импорта: `{ accepted: N, skipped: N, conflicts: [...] }`.

## 10. Ошибки и границы

- Голосовое сообщение из Telegram **> 25 МБ** → отказ с подсказкой использовать веб-загрузку.
- Видеофайл через веб **> 500 МБ** → `413` с подсказкой об ограничении.
- Неподдерживаемый формат файла → `415` с перечнем допустимых форматов.
- STT-провайдер недоступен → `503` с retry-подсказкой; задание остаётся в статусе `pending` для повтора.
- Вебхук без токена или с невалидным → `403`.
- Черновик без заполнения трёх обязательных полей за 24 ч → автоотмена (`cancelled`) с уведомлением в тред/личку.
- Импорт с невалидными строками → строки пропускаются; полный отчёт ошибок в ответе; успешные строки применяются.
- Конфликт версии при ручной правке → `409` с текущей версией объекта; клиент предлагает merge.
- Rate limit webhook: 100 обновлений/минуту на бота → `429` с `Retry-After`.

## 11. Критерии приёмки MVP (пилот)

1. **Текст в канале → запись** с описанием, сроком, ответственным (или цикл уточнений до заполнения).
2. **Голос → то же** (STT → slot-filling → черновик → открытое поручение).
3. **US-C «запись с мероприятия» (Telegram):** аудио **или видео** с совещания, отправленное боту → список черновиков поручений в веб-UI AI PMO; пользователь подтверждает / корректирует.
4. **US-C2 «запись с мероприятия» (Web):** тот же файл загружается через веб-форму AI PMO → тот же экран подтверждения черновиков → поручения открываются в реестре.
5. **За N времени до `due_at`** — сообщение в тот же канал; повторная доставка не создаёт дубль.
6. **Публичный URL реестра** открывается из РФ; отражает последнюю опубликованную версию (≤ 2 мин после публикации).
7. **Выгрузка → правка → импорт → публикация** без расхождений с ожиданием.
8. **Уточняющие вопросы** при нехватке полей; таймаут черновика соблюдается.
9. Повторная доставка одного и того же webhook-сообщения не создаёт дубль в реестре.
10. Все секреты (токены бота, ключи STT, ключи CDN) хранятся только в env; нет в логах.
11. CRUD поручений в рамках проекта; валидация обязательных полей; список с фильтрами (US-5, US-6).
12. Модуль аудита плана не изменён по NFR stateless; домены аудита и BL-6 разделены (нет утечки файлов планов в таблицы поручений).

## 12. Интеграция с фичей «Аудит плана»

Модуль BL-6 разрабатывается в том же приложении (`app/`), что и аудит Excel/CSV (`docs/specs/SPEC-PLAN-AUDIT.md`), но **домены разделены**:

| Тема | Аудит плана | BL-6 |
|------|-------------|------|
| Данные | Stateless, файл не на диске | Postgres, персистентный реестр |
| API | `POST /api/analyze` | `/api/projects/:projectId/assignments`, webhook, ingest |
| Rate limit | По IP/cookie (Free) | Отдельные лимиты на webhook и `/media/ingest` |

**Обязательно:** не смешивать бинарные загрузки планов с таблицами поручений; общие auth и деплой — допустимы. Трек BL-6 можно вести **параллельно** с аудитом после BL1-0 или независимо, если модули изолированы.

## 13. Технологический стек (BL-6)

- **Приложение:** Next.js (App Router), React, TypeScript — каталог `app/`.
- **БД:** PostgreSQL (Supabase), миграции SQL в `supabase/migrations/`.
- **Auth:** Supabase Auth (magic link / OAuth) — см. `docs/plans/BL1-0_KICKOFF.md`.
- **Очередь/крон:** Vercel Cron + outbox-таблица для напоминаний (BL1-4).
- **STT:** SaluteSpeech; **публичный реестр:** Yandex Object Storage + CDN.
- **LLM:** slot-filling и разбиение транскриптов — только нормализованный текст; подтверждение человеком перед `open`.
