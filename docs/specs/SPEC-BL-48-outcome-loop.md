# BL-48 · Project Impact / Outcome Loop

**Статус:** v1.0 — подготовлено 08.11.2026 как отдельная спецификация после P0.
**Основания:** Product Contract v1 (результат ≠ эффект), SPEC-P0 v1.0 §§1, 4, 8, 11.
**Граница:** один проект. BL-48 не заменяет P0 и не объявляет эффект по факту выполнения поручения без фактических данных.

## 1. Цель

Достроить цепочку:

`сигнал → риск → предложение → решение → поручение → результат → подтверждённый эффект`.

BL-48 отвечает не только «что исполнено», но и «что изменилось в ключевых параметрах проекта». Ожидаемый эффект формируется при решении, фактический эффект подтверждается только сопоставимыми измерениями и источниками.

## 2. Инварианты

1. Выполнение Task само по себе не доказывает эффект.
2. Нельзя выдумывать baseline, actual, единицы измерения, источник или численное значение эффекта.
3. Каждое измерение имеет проект, Task/Decision, metric, unit, baseline/target/actual, источник, атрибуцию и время.
4. Подтверждение эффекта возможно только при сопоставимых baseline/target/actual одной метрики и проверяемом источнике.
5. Недостаточность данных — честный статус `unconfirmed`, а не нулевой эффект.
6. РП утверждает управленческие измерения. PMO/аудитор/C-level — read-only. Права проверяются на сервере.
7. Исправление создаёт новую версию измерения, не переписывает прошлое. Повтор одинакового payload идемпотентен.
8. L3 содержит результат, ожидаемый эффект, фактический эффект и его основание либо честное `unconfirmed`.
9. Рабочие Telegram-чаты остаются read-only. Персональные уведомления — только в RP DM.
10. Полный Learning Loop и автоматическая оптимизация решений вне первого среза.

## 3. Объектная модель первого среза

### OutcomeMeasurement

- `id`, `projectId`, `taskId`, `decisionId`.
- `metric`: машинное имя параметра проекта, например `schedule_days`, `cost_amount`, `quality_defects`, `resource_days`.
- `unit`: `days`, `hours`, `currency`, `count`, `percent`, `ratio`.
- `baselineValue`, `targetValue`, `actualValue`: decimal, nullable до фактического измерения.
- `source`: человекочитаемое происхождение данных.
- `sourceId`: стабильный идентификатор первичного источника.
- `sourceUrl`: кликабельный URL либо `null` с честным `unavailable`.
- `status`: `draft`, `confirmed`, `superseded`.
- `version`, `previousVersionId`.
- `recordedByUserId`, `recordedByName`, `recordedByRole`.
- `createdAt`.

### EffectAssessment

Производное значение, не отдельная ручная «оценка РП»:

- `status`: `confirmed` | `unconfirmed`.
- `expectedEffect`: исходный текст Decision.
- `actualEffect`: вычисленный текст либо честное состояние недостаточности данных.
- `basis`: метрика, baseline/target/actual, источник и версия измерения.
- `measurementId`, `createdAt`.

Событие `effect.reported` сохраняет assessment и ссылку на OutcomeMeasurement. Прежнее `result.recorded` не переписывается.

## 4. Правила вычисления

1. Baseline и target берутся из решения/измерения, actual — из фактического источника.
2. Для `schedule_days`: `actualEffect = baselineValue − actualValue`; положительное значение означает сокращение срока.
3. Для остальных метрик первого среза численный эффект не вычисляется автоматически: показываются значения и единица, без выдуманной интерпретации.
4. `confirmed` требует:
   - `metric` и `unit`;
   - baseline и actual;
   - source и sourceId;
   - RP attribution;
   - связь Task ↔ Decision.
5. Отсутствие baseline/actual/источника или несовпадение Task ↔ Decision → `unconfirmed`.
6. Если target отсутствует, факт baseline/actual всё равно допустим для audit, но expected effect не считается достигнутым автоматически.
7. Повтор одинакового `taskId + metric + version` возвращает сохранённое состояние без второй записи/audit event.

## 5. Первый срез реализации

- Аддитивная миграция `0009_bl48_outcome_measurements.sql`.
- Server-only `pmo.recordOutcome` для проектного РП.
- Read-only exposure измерений и assessment в `pmo.state` и Task ↔ Decision ↔ Risk ↔ Signal.
- Обновление L3: использовать фактическое измерение, если оно валидно; иначе прежний честный `unconfirmed`.
- Outcome audit: `outcome.recorded`, `outcome.corrected`, `effect.reported`.
- Идемпотентность record/retry/restart, серверные негативные проверки ролей и отсутствия Task/Decision.

Не входит: автоматический сбор внешних KPI, портфельная аналитика, Learning Loop, автоматическая оптимизация решений, новые каналы, редизайн workspace.

## 6. Критерии приёмки первого среза

- [ ] Без измерения L3 сообщает об недостаточности данных.
- [ ] Валидное измерение `schedule_days` создаёт подтверждённый численный эффект с baseline/target/actual и источником.
- [ ] Источник кликабелен либо честно `unavailable` с sourceId.
- [ ] Повтор одинакового измерения не создаёт вторую запись/audit event.
- [ ] Исправление создаёт новую версию и `outcome.corrected`, прежняя версия сохраняется.
- [ ] PMO/аудитор/C-level не могут записывать измерения даже прямым серверным вызовом.
- [ ] Несвязанные Task/Decision, отсутствие baseline/actual/source и чужой project вызывают ошибку или `unconfirmed`, не фальшивый confirmed.
- [ ] Restart/retry не дублирует измерение и `effect.reported`.
- [ ] BL-35 показывает измерение, assessment и исходную цепочку после restart.
- [ ] Production `.env`, webhook/gateway и рабочие групповые чаты не изменяются; реальные IDs не публикуются.

## 7. Реальная приёмка

1. На уже выполненном P-06 сначала фиксируется прежний `unconfirmed`.
2. РП вводит synthetic, явно тестовое измерение `schedule_days` с baseline/target/actual и источником.
3. Проверяется вычисление, версия, атрибуция, audit и отсутствие дублей.
4. РП исправляет измерение новой версией; исходная версия доступна.
5. Проверяется L3 и BL-35 после restart.
6. Отдельно фиксируется время от сигнала до решения и канал решения.

## 8. Следующие контуры

- Метрики cost/quality/resources с явными формулами.
- Baseline пилота и сравнение через 2–4 недели.
- Learning Loop без автоматического принятия решений.
