# Администратор поручений — план реализации в Cursor (через агентов)

**Статус:** рабочий план для разбиения на PR/ветки и параллельных агентов  
**Связанные артефакты:** карточка в Notion «Бэклог AI PMO», этот файл в репозитории лендинга. **Примечание:** текущее решение команды — **один репозиторий** с лендингом и приложением; старт фазы BL1-0 и зафиксированные допущения см. `docs/BL1-0_KICKOFF.md`. Отдельный app-репозиторий не обязателен.

---

## 1. Цель продукта (MVP+)

Сервис принимает поручения из **Telegram** (текст и голос), ведёт **реестр** с минимальными полями (**описание, срок, ответственный**), задаёт **уточняющие вопросы** при неполных данных, **уведомляет в тот же Telegram-канал** о наступлении срока, публикует **актуальную версию реестра** в открытом доступе с фокусом на **доступность из РФ**, поддерживает **выгрузку** и **ручные правки** с повторной публикацией.

### Улучшения сверх базовых требований

- **Идемпотентность и аудит:** `external_id` (Telegram `message_id` + `chat_id`), журнал изменений, кто и когда поправил запись.
- **Голос:** распознавание речи с приоритетом провайдера, дружественного к RU (например **Yandex SpeechKit** или совместимый STT self-host в РФ); fallback — Whisper-совместимый API вне РФ только если политика данных позволяет.
- **Уточнения:** диалог в **личке с ботом** или **тред под сообщением**, чтобы не засорять канал; таймаут черновика (например 24 ч) и авто-отмена.
- **Напоминания:** за N дней/часов и в день дедлайна; текст с ссылкой на **публичную** строку реестра.
- **Публичный реестр:** статическая выдача **JSON + HTML** (без обязательной авторизации для чтения); версия `ETag`/`updated_at` для кэшей CDN.
- **РФ-доступ:** отдельный деплой фронта/статики на площадку без блокировок (например **Yandex Object Storage + CDN**, **VK Cloud**, **Selectel**, **Timeweb**); не завязывать чтение реестра на домены/CDN, часто фильтруемые в РФ. Международный mirror (Vercel) опционально как вторичный URL.
- **Ручные правки:** защищённая админ-страница или одноразовые **signed links** + CSV/XLSX round-trip; импорт с валидацией и отчётом об ошибках.

## 2. Архитектура (кратко)

```
Telegram (канал/супергруппа) ──► Bot Webhook ──► Ingest + STT + LLM slot-filling
                                        │
                                        ▼
                                 API + DB (Postgres)
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
            Scheduler (cron/queue)   Public static       Admin import/export
            → напоминания в канал    generator/sync      + signed edits
```

- **БД:** Postgres (записи поручений, черновики ожидания ответа, напоминания «уже отправлено»).
- **Очередь (по мере роста):** Redis + worker или managed queue; на MVP — cron + таблица `due_reminders`.

## 3. Работа в Cursor через агентов

### 3.0. Kickoff BL-1 — обязательный первый шаг (до треков A–G)

**Перед** разбиением на параллельные ветки и выдачей треков агентам A–G команда проводит **один сеанс MVP Builder Mode** в Cursor Agent:

1. Подключить skills: `@agents-best-practices` (harness) и `@ai-pmo-assignments` (домен BL-1). Пути: `.cursor/skills/…`, триггеры — в `AGENTS.md`.
2. Запросить blueprint по шаблону из `agents-best-practices/SKILL.md` (секция *MVP Builder Mode*) и reference `references/mvp-agent-blueprint.md`.
3. **Выход сеанса (артефакт в репозитории):** документ уровня `docs/BL1_HARNESS_BLUEPRINT.md` (или согласованное имя) с:
   - core loop (ingest → slot-filling → draft → human confirm → commit);
   - **tool registry** — узкие typed tools (не `send_message` / `write_database` без обёртки);
   - **permission matrix** и точки approval (публикация в канал, публичный реестр, внешние записи);
   - бюджеты цикла (шаги, таймаут черновика, стоимость STT/LLM);
   - **launch gate** — evals и критерии пилота до включения автономных side effects.

Без этого blueprint не стартуют треки B–G с внешними side effects; трек **A** (контракты/схема) может идти параллельно kickoff, но OpenAPI и Zod должны **согласоваться** с итогом сеанса.

**Промпт-заготовка:**

```text
@agents-best-practices @ai-pmo-assignments
Спроектируй MVP harness blueprint для BL-1 «Администратор поручений» по ASSIGNMENTS_ADMIN_CURSOR_PLAN.md.
Уровень: approval-gated (L2). Включи tool registry, permissions, context/compaction для long-running агентов,
launch gate и evals. Сохрани структуру в docs/BL1_HARNESS_BLUEPRINT.md.
```

Статус шага 3 «практичного минимума» Agent Skills — в карточке Notion «Администратор поручений».

---

Ниже — **самостоятельные треки** (после §3.0). Каждый трек можно отдать отдельному Cloud Agent / ветке; контракты между треками зафиксировать в `docs/` или в OpenAPI-черновике до начала кодирования.

### Агент A — Контракты и данные

**Выход:** `lib/types` (или общий пакет), SQL-миграции, ER-диаграмма в комментарии к PR.

- Сущности: `Project`, `Assignment`, `AssignmentEvent`, `ClarificationSession`, `ReminderLog`, `PublicationSnapshot`.
- Поля MVP: `description`, `due_at`, `assignee` (Telegram @username / user_id / отображаемое имя), `status`, `source_message_ref`, `locale`.
- Индексы по `due_at`, `project_id`, `status`.

**Критерий готовности:** миграции накатываются; seed для локальной отладки.

---

### Агент B — Telegram: приём текста и голоса

**Выход:** webhook handler, верифрация `X-Telegram-Bot-Api-Secret-Token`, парсинг `message`, загрузка `voice`/`audio` → STT.

- Команды: `/help`, при необходимости `/link_project` (если несколько проектов на чат).
- Текст: передать в слой нормализации (Агент D).
- Голос: скачать файл, STT, дальше как текст.

**Критерий готовности:** сообщение из тестового канала создаёт или обновляет черновик в БД.

---

### Агент C — Уточняющие вопросы (LLM + состояние)

**Выход:** модуль `clarify`: по неполной структуре генерирует 1–3 вопроса; парсит ответы пользователя.

- Правила: не спрашивать поле, если оно уже извлечено с высокой уверенностью; максимум раундов (например 3).
- Хранение состояния сессии в БД (`ClarificationSession`).
- После заполнения минимума — финализировать `Assignment` и ответить в канал кратким подтверждением (настраиваемо).

**Критерий готовности:** e2e-тест на фикстурах: неполное сообщение → вопросы → финальная запись.

---

### Агент D — Напоминания в канал

**Выход:** worker/cron: выборка `due_at` в окне, антидубли по `ReminderLog`.

- Шаблоны сообщений (RU), ссылка на публичную строку/якорь.
- Конфиг: за сколько часов/дней слать; часовой пояс проекта.

**Критерий готовности:** тестовое поручение с ближайшим сроком получает пост в канал ровно один раз на интервал.

---

### Агент E — Публичный реестр (чтение из РФ)

**Выход:** генератор снапшотов: `registry.json` + `index.html` (таблица, поиск на клиенте), скрипт деплоя в выбранный RU-friendly object storage / static host.

- Сборка без вызовов зарубежных API в runtime читателя (только статика).
- Политика PII: в публичном слое не показывать лишние персональные поля; только согласованные колонки.

**Критерий готовности:** URL открывается из РФ (проверка с VPN/внешним ping); обновление после каждой публикации ≤ 1–2 мин (или по кнопке «Опубликовать»).

---

### Агент F — Выгрузка и ручные корректировки

**Выход:** экспорт CSV/XLSX; импорт с diff-превью; опционально простая админка.

- Экспорт: полный срез + `updated_at`.
- Импорт: сопоставление по `id` или стабильному ключу; отчёт «принято / пропущено / конфликт».
- Ручные правки в UI: optimistic lock по `version`.

**Критерий готовности:** round-trip: экспорт → правка в Excel → импорт → публичный снапшот обновлён.

---

### Агент G — Наблюдаемость и безопасность

**Выход:** структурированные логи, rate limit на webhook, секреты в env, чеклист угроз (подделка webhook, спам в канал).

## 4. Порядок слияния (зависимости)

0. **§3.0 Kickoff BL-1** — MVP Builder Mode → `docs/BL1_HARNESS_BLUEPRINT.md` (блокирует B–G с side effects).  
1. **A** (схема) параллельно с §3.0 и черновиком OpenAPI; финализация схемы — после согласования с blueprint.  
2. **B** + **C** после A и §3.0.  
3. **D** после B+C (нужны финальные записи).  
4. **E** после A (можно параллельно B с мок-данными).  
5. **F** после A и желательно после E (общий формат снапшота).  
6. **G** непрерывно, финальный проход перед пилотом.

---

## 5. Приёмка пилота

- [ ] Текст в канале → запись с описанием, сроком, ответственным (или цикл уточнений до заполнения).  
- [ ] Голос → то же.  
- [ ] За N времени до `due_at` — сообщение в **тот же канал**.  
- [ ] Публичный URL реестра открывается из РФ; отражает последнюю опубликованную версию.  
- [ ] Выгрузка → правка → импорт → публикация без расхождений с ожиданием.  
- [ ] Сервис задаёт уточняющие вопросы при нехватке полей.

## 6. Вне скоупа первой итерации (бэклог рядом)

- Несколько каналов и матрица прав; SSO.  
- Интеграции кроме Telegram (Slack, e-mail).  
- Автоматическое определение ответственного из LDAP/HR.
