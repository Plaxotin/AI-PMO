# Администратор поручений — план реализации в Cursor (через агентов)

**Статус:** актуальный план (синхронизирован со спекой v1.2)  
**Спека:** `docs/SPEC-BL-6-assignments-admin.md` — источник истины по требованиям и зафиксированным решениям  
**Связанные файлы:** `docs/BL1-0_KICKOFF.md`, `docs/BL1-0_VERIFICATION.md`  
**Примечание:** один репозиторий с лендингом и приложением; BL1-0 верифицирована.

---

## 1. Цель продукта (MVP)

Сервис принимает поручения из **Telegram** (текст, голос, видео) и через **веб-форму загрузки** в AI PMO, ведёт **реестр** с полями (**описание, срок, ответственный**), задаёт **уточняющие вопросы в треде** при неполных данных, **уведомляет в тот же Telegram-канал** о наступлении срока, публикует **актуальный реестр** на **Yandex Object Storage** (CDN, доступность из РФ), поддерживает **выгрузку CSV/XLSX** и **ручные правки через signed links**.

**Убийственный сценарий:** аудио- или видеофайл с летучки/созвона → отправить боту в Telegram или загрузить через веб → AI PMO показывает структурированный список поручений с экраном подтверждения.

### Зафиксированные решения (24.05.2026)

| Тема | Решение |
|------|---------|
| STT-провайдер | **[SaluteSpeech (Сбер)](https://developers.sber.ru/docs/ru/salutespeech/overview)** — РФ-контур. Fallback (Whisper-совместимый) только при недоступности и разрешённой политике. |
| CDN публичного реестра | **Yandex Object Storage** + Yandex CDN |
| Хранение медиафайлов | **Не храним.** Файл → tmp/RAM → SaluteSpeech → удалить. Оригинал — только в Telegram-канале или на устройстве. |
| Уточнения (дефолт) | **Тред** под исходным сообщением |
| Авторизация правок | **Одноразовые signed links** |

## 2. Архитектура

```
Telegram (канал / личка)                Web-форма (AI PMO UI)
  │ текст / голос / видео                 │ аудио / видео (≤ 500 МБ)
  ▼                                       ▼
Bot Webhook ──────────────────► Media Ingest (Агент B + H)
                                  │ tmp → SaluteSpeech STT → ffmpeg (видео) → удалить файл
                                  ▼
                          LLM slot-filling / разбиение
                                  │
                         ClarificationSession (тред)   Confirm UI (веб)
                                  │                          │
                                  └──────────┬───────────────┘
                                             ▼
                                       API + DB (Postgres)
                                   ┌────────────────────────┐
                                   │                        │
                         Scheduler (cron/outbox)   Public static generator
                         → напоминания в канал     → registry.json + HTML
                                                   → Yandex Object Storage CDN
                                                   ↑
                                       Import / Export / Signed-link edits
```

- **БД:** Postgres — `assignments`, `clarification_sessions`, `reminder_logs`, `media_ingest_jobs`, `publication_snapshots`.
- **Очередь на MVP:** cron + таблица `due_reminders` + `media_ingest_jobs` (статусы: `pending | processing | done | failed`).
- **Медиафайлы:** через tmp/RAM, не сохраняются в БД и Object Storage.

## 3. Агенты Cursor

Каждый трек — отдельный Cloud Agent / ветка. Контракты зафиксировать в `docs/` или OpenAPI-черновике до начала кодирования.

---

### Агент A — Контракты и данные

**Выход:** Zod-типы, SQL-миграции v2+, seed для локальной отладки, ER-комментарий к PR.

**Сущности:**

| Сущность | Ключевые поля |
|----------|--------------|
| `Assignment` | `id`, `project_id`, `title`, `description`, `status` (`draft\|open\|done\|cancelled`), `due_at`, `assignee`, `source` (`manual\|import\|webhook\|web_upload`), `version`, `created_at`, `updated_at` |
| `AssignmentEvent` | журнал смен статуса и полей |
| `ClarificationSession` | `assignment_id`, `thread_message_id`, `rounds`, `expires_at` |
| `ReminderLog` | `(assignment_id, reminder_type)` — антидубли |
| `MediaIngestJob` | `id`, `project_id`, `source` (`telegram\|web`), `status`, `transcript` (text), `drafts` (jsonb), `created_at` |
| `PublicationSnapshot` | `project_id`, `url`, `etag`, `published_at` |

**Индексы:** `due_at`, `project_id`, `status`, `(assignment_id, reminder_type)`.

**Критерий готовности:** миграции накатываются на чистую БД; seed генерирует тестовые записи; Zod-типы экспортированы и не расходятся со схемой.

---

### Агент B — Telegram: приём текста, голоса и видео

**Выход:** webhook handler + STT-pipeline для Telegram-сообщений.

**Scope:**

- Верификация `X-Telegram-Bot-Api-Secret-Token`.
- Парсинг `message`: тип (`text | voice | audio | video | video_note`), `chat_id`, `message_id`.
- Идемпотентный ключ `chat_id + message_id` — повторная доставка не создаёт дубль.
- **Текст** → передать в слой нормализации (Агент C).
- **Голос/аудио** (`voice`, `audio`): скачать в tmp → **SaluteSpeech** STT → удалить файл → передать транскрипт в Агент C.
- **Видео** (`video`, `video_note`): скачать в tmp → **ffmpeg** извлечь аудиодорожку → **SaluteSpeech** STT → удалить оба файла → передать транскрипт в Агент C.
- Для файлов, превышающих лимит Telegram (обычно 20 МБ через Bot API): ответить в тред с подсказкой загрузить через веб-форму.
- Команды бота: `/help`; опционально `/link_project` (если несколько проектов на чат).

**Зависимости:** Агент A (схема `MediaIngestJob`, `ClarificationSession`).

**Env-переменные:** `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `SALUTESPEECH_CLIENT_ID`, `SALUTESPEECH_SECRET`.

**Критерий готовности:**
- Текст из тестового канала → черновик `Assignment` в БД.
- Голосовое сообщение → транскрипт → черновик.
- Видео (тестовый ролик ≤ 20 МБ) → извлечь аудио → транскрипт → черновик.
- Повторная доставка того же `message_id` → черновик не дублируется.
- Медиафайл не остаётся в tmp после успешной обработки.

### Агент H — Веб-загрузка медиафайлов (US-C2)

**Выход:** API медиа-инжеста через веб + экран подтверждения черновиков в UI.

**Scope (API):**

```
POST /api/projects/:projectId/media/ingest
     multipart/form-data:
       file          — аудио (.mp3 .m4a .ogg .wav .opus)
                       или видео (.mp4 .mov .webm .mkv), ≤ 500 МБ
       meeting_title — (опц.) название мероприятия
       meeting_date  — (опц.) ISO-8601
       participants  — (опц.) JSON-массив @username / имён участников

GET  /api/projects/:projectId/media/ingest/:jobId
     → { status, progress_pct, error? }

GET  /api/projects/:projectId/media/ingest/:jobId/drafts
     → { drafts: [{ id, title, due_at?, assignee?, confidence }] }

POST /api/projects/:projectId/media/ingest/:jobId/confirm
     { accepted: [id,...], rejected: [id,...], overrides: { id: {...} } }
     → принятые черновики → Assignment.status = 'open'
```

**Scope (pipeline):**

- Принять файл, сохранить в tmp/RAM.
- Для видео: ffmpeg → аудиодорожка; для аудио — напрямую.
- **SaluteSpeech** STT → транскрипт.
- Удалить медиафайл немедленно.
- LLM: разбить транскрипт на отдельные поручения; для каждого — `title`, `due_at` (если упомянут), `assignee` (по `participants` или эвристике).
- Сохранить черновики в `MediaIngestJob.drafts` (jsonb).
- Файлы > 25 МБ: обработка асинхронно; статус через polling `GET …/:jobId` или SSE.

**Scope (UI — страница проекта):**

- Форма загрузки с полями: файл, `meeting_title`, `meeting_date`, `participants`.
- Прогресс-бар/spinner во время обработки (polling/SSE).
- Экран подтверждения: список черновиков с возможностью отредактировать каждый, принять или отклонить.
- После confirm — редирект на реестр с отображением новых записей.

**Ошибки:**
- > 500 МБ → `413` с подсказкой.
- Неподдерживаемый формат → `415` с перечнем.
- SaluteSpeech недоступен → `503`; `job.status = 'failed'`; пользователь может повторить.

**Зависимости:** Агент A (схема `MediaIngestJob`), Агент B (общий SaluteSpeech-клиент и ffmpeg-утилита).

**Критерий готовности:**
- mp3-файл (запись голоса) → загрузить через форму → список черновиков → подтвердить → поручения в реестре.
- mp4-файл (экранная запись с аудио) → тот же результат.
- Файл удалён с сервера до ответа `/confirm`.
- При загрузке файла > 500 МБ — корректная ошибка `413`.

### Агент C — LLM slot-filling и уточняющие вопросы

**Выход:** модуль `clarify` — нормализация текста в поля поручения + диалог уточнений в треде.

**Scope:**

- Принять текст (из Агента B или напрямую) → LLM slot-filling: извлечь `title/description`, `due_at` (нормализовать дату), `assignee`.
- Если поле не извлечено или confidence < порога — добавить в очередь уточнений.
- **Уточнения в треде** (зафиксировано): бот отвечает в тред под исходным сообщением, не в основной поток канала.
- Максимум 3 раунда уточнений; таймаут черновика — 24 ч; по истечении → `Assignment.status = 'cancelled'`, уведомление в тред.
- LLM задаёт ≤ 3 вопросов за раунд; не переспрашивает поля с высоким confidence.
- После заполнения трёх обязательных полей (`title`, `due_at`, `assignee`) → `Assignment.status = 'open'`; краткое подтверждение в тред.
- Хранение состояния: `ClarificationSession` (БД).

**Данные, уходящие в LLM:** только нормализованный транскрипт + текущий черновик полей. Полный лог канала не передаётся.

**Зависимости:** Агент A, Агент B (входящий транскрипт).

**Критерий готовности:** e2e-тест на фикстурах:
- Неполное сообщение (нет срока) → вопрос в тред → ответ пользователя → финальная запись `open`.
- Черновик без ответа 24 ч → `cancelled`, уведомление в тред.
- Полное сообщение → никаких вопросов, сразу `open`.

### Агент D — Напоминания в канал

**Выход:** worker/cron — антидубли, шаблоны, ссылка на публичную строку реестра.

**Scope:**

- Cron-задание: выборка `Assignment` с `due_at` в настроенных окнах (за N дней/часов до дедлайна, в день дедлайна).
- Антидубли: проверка `ReminderLog` по `(assignment_id, reminder_type)` перед отправкой.
- Шаблон сообщения (RU): описание · срок · ответственный · ссылка на публичную строку реестра (`<YOS_URL>/registry.html#<id>`).
- Конфигурация: интервалы напоминаний и часовой пояс — на уровне проекта; флаг выключения.

**Зависимости:** Агент A, Агент C (нужны финальные записи со статусом `open`), Агент E (нужен публичный URL строки реестра).

**Критерий готовности:** тестовое поручение с `due_at` через 1 ч → ровно одно сообщение в канал на интервал; повторный запуск cron → не дублирует.

---

### Агент E — Публичный реестр (Yandex Object Storage)

**Выход:** генератор снапшота + скрипт деплоя в Yandex Object Storage.

**Scope:**

- Генерация `registry.json` (массив поручений, только согласованные колонки без лишнего PII) + `index.html` (таблица, клиентский поиск/фильтр, без зарубежных runtime-зависимостей).
- Версионирование: `updated_at`, ETag в заголовке ответа Object Storage.
- **Деплой:** `aws s3 cp` / `rclone` / Yandex Cloud CLI (`yc`) → bucket + Yandex CDN. URL формата `https://<bucket>.storage.yandexcloud.net/registry.json`.
- Публикация запускается: автоматически после подтверждения черновиков или ручной правки; вручную — `POST /api/projects/:projectId/publish`.
- Обновление CDN ≤ 1–2 мин после деплоя (CDN invalidation или короткий TTL).

**Env-переменные:** `YOS_ACCESS_KEY_ID`, `YOS_SECRET_ACCESS_KEY`, `YOS_BUCKET`, `YOS_CDN_BASE_URL`.

**Зависимости:** Агент A (схема `PublicationSnapshot`); можно параллельно с B+C на мок-данных.

**Критерий готовности:** `registry.json` и `index.html` задеплоены; URL открывается из РФ (проверка через внешний IP/VPN); после публикации новой записи обновление видно ≤ 2 мин.

---

### Агент F — Выгрузка и ручные правки

**Выход:** экспорт CSV/XLSX; импорт с diff; signed-link механизм правок.

**Scope:**

- **Экспорт:** `GET /api/projects/:projectId/assignments/export?format=csv|xlsx` — полный срез с `updated_at`.
- **Импорт:** `POST .../import` (multipart) — валидация, сопоставление по `id`, отчёт `{ accepted, skipped, conflicts }`, опционально diff-превью перед применением. Optimistic lock по `version`.
- **Signed links** (зафиксировано): генерация одноразовой ссылки для редактирования конкретной записи; ссылка невалидна после использования или по TTL (например 15 мин). Никаких отдельных защищённых admin-страниц в MVP.
- После любой правки или импорта → тригер публикации снапшота (Агент E).

**Зависимости:** Агент A, Агент E (общий формат снапшота).

**Критерий готовности:** round-trip: экспорт → правка поля в Excel → импорт → `registry.json` обновлён и отражает правку. Signed link работает ровно один раз.

---

### Агент G — Наблюдаемость и безопасность

**Выход:** структурированные логи, rate limit, чеклист угроз, верификация no-storage policy.

**Scope:**

- Структурированные JSON-логи на каждое событие: webhook получен, STT-запрос, LLM-запрос, запись создана/изменена, напоминание отправлено, деплой запущен.
- **Rate limit** webhook: 100 обновлений/мин на бота → `429 Retry-After`.
- **Rate limit** `/media/ingest`: настраиваемый лимит по `project_id` (по умолчанию 10 запросов/ч).
- Все секреты — только из env; ни один не попадает в логи (маскирование).
- **Верификация no-storage:** интеграционный тест/скрипт проверяет, что в tmp нет медиафайлов через 60 с после успешного STT-вызова.
- Чеклист угроз: подделка webhook (митигация — верификация токена), спам в канал (rate limit), replay-атаки (идемпотентный ключ), утечка PII через снапшот (только согласованные колонки).

**Зависимости:** все агенты; финальный проход перед пилотом.

**Критерий готовности:** повторная доставка webhook → без дублей; секреты не в логах; нет медиафайлов в tmp после обработки; rate limit возвращает `429` при превышении.

## 4. Порядок слияния (зависимости)

1. **A** (схема + миграции) — параллельно с OpenAPI-черновиком.
2. **B** + **C** — после A.
3. **H** (веб-загрузка) — после A и после B (общий SaluteSpeech-клиент и ffmpeg-утилита).
4. **D** (напоминания) — после B + C (нужны финальные записи `open`).
5. **E** (YOS-реестр) — после A; можно параллельно с B на мок-данных.
6. **F** (импорт/экспорт/signed links) — после A и E (общий формат снапшота).
7. **G** — непрерывно по всем PR; финальный аудит-проход перед пилотом.

## 6. Приёмка пилота

- [ ] Текст в канале → запись с описанием, сроком, ответственным (или цикл уточнений в треде до заполнения).
- [ ] Голосовое сообщение → SaluteSpeech → то же.
- [ ] Видео из Telegram → ffmpeg → SaluteSpeech → то же.
- [ ] **US-C (Telegram):** аудио- или видеофайл с летучки → боту → список черновиков в веб-UI → подтверждение → поручения `open`.
- [ ] **US-C2 (Web):** тот же файл через веб-форму → тот же экран подтверждения → поручения `open`.
- [ ] Медиафайл удалён с сервера до завершения ответа (нет в tmp после обработки).
- [ ] Уточняющие вопросы задаются в треде; черновик без ответа 24 ч → `cancelled`.
- [ ] За N времени до `due_at` — ровно одно сообщение в канал (без дублей при повторе).
- [ ] Публичный URL реестра (YOS) открывается из РФ; обновляется ≤ 2 мин после публикации.
- [ ] Выгрузка → правка в Excel → импорт → снапшот обновлён и задеплоен.
- [ ] Signed link для правки работает ровно один раз.
- [ ] Повторная доставка webhook с тем же `message_id` — без дублей.
- [ ] Все секреты только в env; нет в логах.

## 7. Вне скоупа первой итерации (бэклог)

- Диалог уточнений в личке с ботом (только тред в MVP).
- Несколько каналов и матрица ролей; SSO / корпоративный LDAP.
- Интеграции кроме Telegram (Slack, e-mail).
- Автоматическое определение ответственного из LDAP/HR по @username.
- Хранение и архив медиафайлов (в MVP — не храним).
- Сложная LLM-дедупликация поручений по семантике.
- Мобильное приложение / PWA.
