## 5. Дополнительная реальная приёмка после подтверждения

18-check contract не заменяет реальную миграцию и restart acceptance.

### B1. Исходный сигнал и роль участника

1. Зафиксировать счётчики тестовых сущностей и audit events.
2. Участник отправляет один согласованный рисковый сигнал до миграции.
3. Проверить один Signal → Risk → Proposal, источник и confidence.
4. Участник отправляет прямой Accept callback: состояние не меняется, Decision/Task не создаются, отказ наблюдаем.

### B2. Контрольная миграция

1. Перевести выделенную тестовую группу в супергруппу.
2. Проверить обработку `migrate_to_chat_id` и `migrate_from_chat_id`.
3. Повторить migration update в контролируемом replay: один канал, два связанных external ID, старый alias `migrated`, новый `active`, ровно один `channel.migrated`.
4. Убедиться, что старая цепочка и исходная ссылка не потеряны.

### B3. Продолжение цепочки после миграции

1. РП открывает исходный риск и принимает предложение уже после миграции.
2. Проверить ровно один Decision и один атомарно связанный Task с корректной атрибуцией РП.
3. Повторить Accept: новых Decision, Task и фактических audit events нет.
4. Участник фиксирует результат; Task получает результат и статус исполнения.
5. Отправить одно согласованное нерисковое сообщение в новом чате: оно связывается с тем же каналом и не порождает новый риск.

### B4. Multi-chat и негативные роли

1. Во втором разрешённом чате выполнить только безопасную команду статуса; проверить тот же проект и отсутствие лишних рисков.
2. Чужой чат и неизвестный пользователь игнорируются.
3. РП сохраняет права после миграции; участник не получает Accept/Reject даже прямым callback.

### B5. Restart и replay

1. На test server выполнить restart между сохранёнными шагами цепочки, затем повторить входящий update и callback через контролируемый harness.
2. Проверить отсутствие потерь необработанных событий и дублей Signal, Risk, Proposal, Decision, Task, Result и AuditEvent.
3. После restart повторно прочитать тестовую БД и сравнить связи, версии, статусы и число событий со snapshot.
4. Production restart отдельно не выполняется без действия владельца.

### B6. Сквозные ссылки

1. Из Task восстановить Task → Decision → Risk → Signal → исходное сообщение.
2. Из Decision открыть Proposal и исходную версию.
3. Проверить старую ссылку до миграции и новые события после миграции в одном канале аудита.
4. Кликабельность Telegram source links проверить в авторизованном клиенте тестового контура; недоступный источник должен иметь честный статус и сохранённый идентификатор, а не подменную ссылку.
5. В evidence сохранить только sanitized связи и результаты переходов, без реальных chat/user IDs.
