# BL-50 · Commitment Tracking — сценарий отдельного реального пилота

**Дата:** 10.11.2026

**Статус:** подготовлено, не выполнялось. Требуется отдельное подтверждение владельца.

**Граница:** один реальный рабочий сигнал и один проект. Не создавать тестовый бизнес-эффект и не менять production до отдельного решения о release.

## 1. Что подтверждено заранее

- Изолированный contract BL-50: **15/15**, включая Accept/Edit/Reject/merge/update, исходы, RBAC, идемпотентность и restart.
- Unit: **49/49**; typecheck, production build и полный regression пройдены.
- GitHub `main`: `ca4b0bd` — реализация BL-50.
- Production на момент подготовки сценария не содержит BL-50; миграция `0011_bl50_commitment_tracking` там не применялась.

Изолированные проверки не являются реальной приёмкой Telegram/AI и не доказывают качество выделения обязательств на рабочей переписке.

## 2. Данные, которые выбирает владелец

До запуска владелец указывает:

1. Один существующий проект и разрешённый рабочий чат, уже доступный текущему read-only контуру BL-36.
2. Одно новое реальное рабочее сообщение с конкретным обязательством, ответственным и сроком. Сообщение отправляет уполномоченный участник после начала пилота; историю чата специально не выгружаем.
3. РП, который будет проверять кандидат и принимать решение.
4. Окно пилота и допустимость одного личного системного предложения РП. Исходящих сообщений в рабочую группу быть не должно.

В sanitized evidence не входят текст сообщения, персональные chat/user IDs, токены и webhook secrets. Их защищённые технические значения используются только для трассировки во время пилота.

## 3. Запреты

- Не использовать выдуманное обязательство как реальный факт проекта.
- Не принимать кандидат автоматически и не подменять решение РП controlled callback без пометки способа проверки.
- Не закрывать Task и не записывать `on_time`/`late` до фактического результата.
- Не отправлять сообщения в рабочую группу, не менять webhook/gateway, `.env`, canonical UI и существующие credentials.
- Не выполнять production cleanup и не удалять пилотные записи после приёмки.
- Не разворачивать BL-55 только потому, что он находится в том же GitHub `main`; объём release фиксируется отдельно.

## 4. Этап A — read-only подготовка

1. Зафиксировать текущий production release, `active/running`, `NRestarts`, landing/workspace HTTP 200.
2. Проверить, что GitHub `main` содержит `ca4b0bd`, а contract BL-50 остаётся 15/15.
3. Определить следующие свободные служебные IDs непосредственно перед выполнением; не переносить коды из других пилотов.
4. Зафиксировать выбранные project/chat/RP в защищённом run record, а в отчёте использовать только псевдонимы `PROJECT-BL50`, `SOURCE-BL50`, `RP-BL50`.
5. Отдельно согласовать release и аддитивную миграцию `0011` через Drizzle. Перед ними — проверенный backup БД и SHA-256.

## 5. Этап B — один реальный сигнал и решение РП

1. Уполномоченный участник отправляет одно согласованное реальное рабочее сообщение.
2. Система через существующий канал создаёт не более одного `CommitmentCandidate` со статусом `pending` либо `pending_merge`.
3. Проверить проект, источник, `evidenceVersion`, `evidenceHash`, заголовок, ответственного, срок, `changeType` и confidence. До решения РП новых Decision/Task быть не должно.
4. Если AI допустил реальную ошибку, РП использует Edit и исправляет только ошибочные поля. Сохраняются исходная версия, diff и editDistance. Если правка не нужна, искусственно её не создавать.
5. РП принимает кандидат. Для `create` атомарно создаются один Decision и один Task; для `update` меняется только срок согласованной существующей Task с old/new.
6. Проверить RP attribution, source linkage и audit `commitment.proposed`, `commitment.accepted`, а при наличии правки — `commitment.edited`/`commitment.rescheduled`.
7. Повторить технически тот же callback и входящий webhook в контролируемом тесте доставки: новых Candidate, Decision, Task, изменения срока и повторного audit быть не должно.

Если кандидат ошибочно получил `pending_merge`, РП не принимает новый Task: сначала проверяется существующая Task и выполняется согласованный merge. Такой случай фиксируется как фактический результат пилота, а не принудительно обходится.

## 6. Этап C — restart, результат и Learning Loop

1. Выполнить один штатный restart и проверить service, `NRestarts`, landing/workspace HTTP 200.
2. Повторная доставка после restart не создаёт дублей и не инициирует незапланированные исходящие сообщения.
3. BL-35 показывает Candidate, источник, статус, версии, решение РП и связь Decision/Task без персональных ID в публичном evidence.
4. После фактического выполнения ответственный/РП фиксирует результат существующим контуром. Проверяются одна `CommitmentOutcome`, дата завершения и корректный `on_time` либо `late`.
5. Если работа не завершена в окне пилота, Outcome остаётся незаполненным, а этот пункт переносится на дату фактического результата. `unknown` не выдаётся за успех.
6. BL-48 получает только реальный Outcome; оценка бизнес-эффекта не создаётся автоматически из факта выполнения.
7. BL-55 показывает фактические acceptance/edit/outcome метрики с честным малым N и `null` при нулевом знаменателе. Предложение логики не утверждать и не применять в этом пилоте.

## 7. Что остаётся доказанным изолированно

Не создавать дополнительные production-сообщения только ради повторения уже пройденных веток:

- Reject с `not_commitment`, `already_done`, `wont_do`;
- повторное отклонение по тем же доказательствам как `ignored`;
- merge по сходству ≥ 0.92;
- несуществующая/чужая `existingTaskId`;
- обычное обсуждение без Candidate;
- AI failure без Risk/Decision/Task и без слепого retry;
- запрет действий PMO/аудитора/C-level/member;
- `late`, `ignored`, `unknown` на synthetic fixtures.

Эти ветки имеют contract evidence, но не маркируются как реальные пользовательские действия.

## 8. Критерии завершения реального пилота

- [ ] Ровно один согласованный реальный сигнал прошёл существующий read-only контур.
- [ ] Кандидат и его доказательства проверены РП; до Accept нет Decision/Task.
- [ ] Accept/фактический Edit создали только разрешённые записи и audit.
- [ ] Повтор webhook/callback и restart не создали дублей.
- [ ] В рабочую группу не отправлено сообщений; незапланированных личных отправок нет.
- [ ] BL-35 отображает сквозную связь и версии.
- [ ] Outcome записан только после фактического результата либо честно перенесён.
- [ ] BL-48/BL-55 не показывают выдуманный эффект или статистическую точность при N=1.
- [ ] Service и HTTP-проверки зелёные; sanitized evidence не содержит secrets и персональных IDs.
- [ ] Владелец отдельно подтвердил результат пилота.

## 9. Откат

При функциональной ошибке остановить пилот и вернуть предыдущий release по штатному runbook. Аддитивные таблицы и уже созданные реальные записи не удалять автоматически; их разбор выполняется отдельно. Не повторять исходящую отправку при неизвестном результате доставки.
