# AI PMO — передача работы и следующие этапы

Дата снимка: 25 октября 2026.

## Текущее состояние

Актуальный production-контур платформы включает лендинг, веб-реестр, server-side проектное состояние и реальный Telegram-сценарий. Исходный Next.js-компонент `app/`, отдельные боты, спеки и статический Vercel-лендинг сохраняются как самостоятельные части продукта.

- Лендинг: https://4nbbao3eiuuc6.kimi.pro/landing.html
- Воркспейс: https://4nbbao3eiuuc6.kimi.pro/workspace.html
- Telegram webhook: `POST /api/telegram/webhook`

Уже принято в production:

- серверный реестр проекта PRJ-01 и атомарная цепочка «решение → поручение»;
- реальный Telegram webhook с проверкой секрета, allowlist чатов и ролями РП/участник;
- несколько проектных Telegram-чатов;
- controlled HTTPS gateway для исходящих вызовов Bot API;
- сквозной реальный сценарий от сигнала до сохранённого результата и аудита;
- дедупликация повторных updates и повторных решений.

Telegram уже настроен. Повторно выпускать токен, менять webhook или пересоздавать gateway при переносе работы не требуется.

## Статус синхронизации исходников

На дату этого снимка полное дерево новой платформы ещё не синхронизировано с GitHub: текущее OAuth-подключение не имеет права на one-time import workflow, а доступный файловый API не переносит binary assets полноценным git-потоком. Не создавать видимость завершённого переноса частичной или неработающей копией. Для синхронизации использовать полноценный git push из защищённого рабочего окружения и отдельный каталог `apps/pmo-platform/`, не перезаписывая существующий `app/`.

Перед переносом удалить из публичной копии реальный encrypted production payload из `api/telegram/config.ts`: production использует его из-за особенностей публикации, но публичный репозиторий должен получать настройки только из server-side environment. Не переносить `.env`, `.credentials/`, пароли VPS, tokens, webhook/gateway secrets и runtime-дампы с персональными данными.

## Обязательные продуктовые рамки

- Scope — отдельный проект, не программа и не портфель.
- Telegram, почта и MAX — место ежедневного действия; веб — проверка, исправление и аудит.
- Только РП утверждает управленческие предложения; C-level — read-only.
- Экран решений эталонный, полный редизайн не нужен.
- Эталонную PNG-иллюстрацию не менять.
- Не объявлять Email или MAX подключёнными до реального сквозного теста.

## Порядок следующих этапов

1. **Синхронизация кода:** полноценный git push sanitized source в `apps/pmo-platform/`; проверить tree, build и secret scan.
2. **Email end-to-end:** входящий сигнал, риск/предложение, решение РП, поручение и результат; отдельная приёмка реальными письмами.
3. **MAX:** тот же контур и ролевая модель после появления реальных доступов к каналу.
4. **Дайджесты и уведомления:** автоматические L2-дайджесты, уведомления о решениях и напоминания по поручениям.
5. **Надёжная исходящая очередь:** persisted queue, идемпотентность, безопасные retry, dead-letter/ручное восстановление, мониторинг.
6. **Telegram migrations:** обработка `migrate_to_chat_id` / `migrate_from_chat_id`, чтобы group → supergroup не требовала ручной смены конфигурации.
7. **Расширение доступов:** дополнительные project chat IDs и member IDs без изменения кода.
8. **Старый мониторинг:** отдельно решить, удалять ли `@PMO_vision_bot` только из текущей группы; глобально сервис не останавливать. После удаления прекратятся его старые дайджесты в этой группе.
9. **Финальная приёмка:** сценарии реальных пользователей, роли, ошибки каналов, восстановление и эксплуатационная инструкция.

## Как начать новую сессию

1. Прочитать этот файл, `AGENTS.md` и действующие спеки в `docs/specs/`.
2. В рабочем окружении владельца найти актуальный проект и полный handoff; GitHub не является источником секретов.
3. Сверить рабочую ветку и production перед изменениями; не считать задокументированный статус заменой проверке.
4. Не запрашивать повторную настройку уже работающего Telegram без диагностики.
5. Выбрать один этап и записать критерии приёмки. Для Email начать с входящего письма и закончить сохранённым результатом.
6. Перед публикацией выполнить typecheck/tests/build, затем контрактную и реальную проверку затронутого канала.
7. Сохранить отдельную версию для отката. Публикацию выполняет владелец продукта.
8. После приёмки обновить этот handoff и репозиторий, не добавляя runtime-дампы с персональными данными.

## Границы безопасной передачи

В GitHub передаются код, placeholders и воспроизводимые тесты. Production `.env`, `.credentials/`, пароли VPS, токены, webhook/gateway secrets, реальные ciphertext и дампы с персональными данными остаются только в защищённом окружении владельца.
