# AI PMO — передача работы и следующие этапы

Дата снимка: 25 октября 2026.

## Текущее состояние

Актуальный production-контур платформы включает лендинг, веб-реестр, server-side проектное состояние и реальный Telegram-сценарий. Исходный Next.js-компонент `app/`, отдельные боты, спеки и статический Vercel-лендинг сохраняются как самостоятельные части продукта.

- Лендинг: https://4nbbao3eiuuc6.kimi.pro/landing.html
- Воркспейс: https://4nbbao3eiuuc6.kimi.pro/workspace.html
- Telegram webhook: `POST /api/telegram/webhook`

Уже принято в production:

- серверный реестр проекта PRJ-01 и атомарная цепочка «решение → поручение»;
- реальный Telegram webhook с проверкой секрета, allowlist чатов и ролями РП/участник;
- несколько проектных Telegram-чатов;
- controlled HTTPS gateway для исходящих вызовов Bot API;
- сквозной реальный сценарий от сигнала до сохранённого результата и аудита;
- дедупликация повторных updates и повторных решений.

Telegram уже настроен. Повторно выпускать токен, менять webhook или пересоздавать gateway при переносе работы не требуется.

## Статус синхронизации исходников

Полное дерево новой платформы ещё не синхронизировано с GitHub: текущее OAuth-подключение не имеет права на one-time import workflow, а доступный файловый API не переносит binary assets полноценным git-потоком. Не создавать видимость завершённого переноса частичной или неработающей копией. Для синхронизации использовать полноценный git push из защищённого рабочего окружения и отдельный каталог `apps/pmo-platform/`, не перезаписывая существующий `app/`.

Перед переносом удалить из публичной копии реальный encrypted production payload из `api/telegram/config.ts`: production использует его из-за особенностей публикации, но публичный репозиторий должен получать настройки только из server-side environment. Не переносить `.env`, `.credentials/`, пароли VPS, tokens, webhook/gateway secrets и runtime-дампы с персональными данными.

## Обязательные продуктовые рамки

- Scope — отдельный проект, не программа и не портфель.
- Telegram, почта и MAX — место ежедневного действия; веб — проверка, исправление и аудит.
- Только РП утверждает управленческие предложения; C-level — read-only.
- Экран решений эталонный, полный редизайн не нужен.
- Эталонную PNG-иллюстрацию не менять.
- Не объявлять Email или MAX подключёнными до реального сквозного теста.

## Правило спецификаций

Все изменения в коде, за исключением дебагинга, выполнять только на основе актуальной спецификации, связанной с задачей в [Бэклоге AI PMO](https://app.notion.com/p/32d71c1c84004354ae367b2886ced001). Перед работой зафиксировать BL-код, спецификацию и критерии приёмки.

Если задачи или спецификации нет, она устарела или противоречит текущему решению, **сначала уведомить пользователя и получить решение по актуализации — только затем менять код**. Дебагинг не должен становиться способом обойти правило: если исправление меняет поведение, интерфейс, роли, данные или интеграционный контракт, спецификация обязательна.

## Этапы и задачи бэклога

На 25.10.2026 статусы BL-36, BL-40 и BL-41 в Notion — «В работе»: реальный базовый сценарий принят, полные AC не закрыты. SPEC-BL-36 архивная. У BL-52, BL-43, BL-54, BL-11, BL-37, BL-42, BL-40 и BL-41 спецификация в свойстве не привязана. Это обязательная точка остановки перед разработкой.

1. **GitHub sync — отдельной BL-задачи не найдено.** Техническая передача без нового поведения: полноценный git push sanitized source в `apps/pmo-platform/`, проверка tree/build/secrets. Изменения поведения требуют отдельной привязки к BL и спецификации.
2. **Email — BL-52; связанные BL-41/BL-40.** Dedicated mailbox без доступа к ящикам сотрудников, CC/пересылка, треды, вложения, dedupe, общая цепочка и исходящие письма с решениями. Спецификация не привязана — сначала уведомить пользователя.
3. **MAX — BL-43; транспорт для BL-41/BL-11/BL-37.** Тот же контур и роли, fallback на Telegram. Спецификация не привязана — сначала уведомить пользователя.
4. **Дайджесты — BL-54 (first value ≤ 24 ч), BL-11 (executive), BL-37 (weekly); решения — BL-41; SLA/напоминания — BL-42.** Согласовать расписание, тишину, получателей и dedupe. Спецификации не привязаны — сначала актуализация.
5. **Исходящая очередь — сквозная надёжность BL-36/BL-52/BL-43/BL-42; отдельной задачи и спеки не найдено.** Persisted queue, идемпотентность, безопасные retry, dead-letter, восстановление и мониторинг. До кода пользователь должен решить: новая BL-задача или расширение спецификаций каналов.
6. **Telegram migrations — BL-36.** Обработка `migrate_to_chat_id` / `migrate_from_chat_id` без ручной смены chat ID и потери аудита. SPEC-BL-36 архивная — сначала уведомить пользователя.
7. **Расширение доступов — BL-36; zero-touch onboarding — BL-31.** Дополнительные project chat IDs и member IDs через server-side config. Конфигурация без кода допустима; изменения onboarding/UI/поведения требуют спецификации.
8. **Старый мониторинг — эксплуатация BL-36 без кода.** Решить удаление `@PMO_vision_bot` только из текущей группы; глобально сервис не останавливать. После удаления прекратятся его старые дайджесты в этой группе.
9. **Финальная приёмка — BL-54; BL-35; AC BL-36/BL-40/BL-41/BL-42.** Реальные пользователи, роли, ошибки каналов, повторная доставка, восстановление и эксплуатационная инструкция. Дефекты — дебагинг; новое поведение — через спецификацию.

## Как начать новую сессию

1. Прочитать этот файл, `AGENTS.md` и действующие спеки в `docs/specs/`.
2. Найти актуальный проект и полный handoff; GitHub не является источником секретов.
3. Сверить ветку и production; не считать документ заменой проверке.
4. Не настраивать заново уже работающий Telegram без диагностики.
5. Выбрать этап, проверить BL-код и спецификацию. Если спеки нет или она устарела — сначала уведомить пользователя.
6. Для Email использовать BL-52 и сначала согласовать критерии приёмки, не начиная разработку автоматически.
7. Перед публикацией выполнить typecheck/tests/build, затем контрактную и реальную проверку канала.
8. Сохранить отдельную версию для отката. Публикацию выполняет владелец продукта.
9. После приёмки обновить handoff и статусы бэклога без runtime-дампов с персональными данными.

## Границы безопасной передачи

В GitHub передаются код, placeholders и воспроизводимые тесты. Production `.env`, `.credentials/`, пароли VPS, токены, webhook/gateway secrets, реальные ciphertext и дампы с персональными данными остаются только в защищённом окружении владельца.
