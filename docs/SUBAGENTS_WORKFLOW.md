# Cursor subagents workflow

Этот протокол описывает трех субагентов для разработки в Cursor Cloud: `Planner`, `Implementer` и `Verifier`. Он нужен, чтобы фазы выполнялись последовательно, без конфликтов за файлы, ветки и решения.

## Важно: это роли, а не встроенные типы Cursor

Проектные custom subagents (`planner`, `implementer`, `verifier`) лежат в `.cursor/agents/` и вызываются как `/planner`, `/implementer`, `/verifier` или через автоделегирование Agent. См. [Cursor Subagents](https://cursor.com/docs/subagents).

Отдельно Cursor предоставляет встроенные субагенты **Explore**, **Bash** и **Browser** (поиск по коду, shell, браузер). Agent подключает их сам; их не нужно дублировать в репозитории.

Репозиторий не может добавить новые значения `subagent_type` в инструмент Task Cloud Agent. Там остаются платформенные типы (`generalPurpose`, `explore`, `debug`, `computerUse`, `videoReview`, `cursor-guide`, `best-of-n-runner` и др.) — их используют только как fallback, передавая prompt роли из этого документа.

`Planner`, `Implementer` и `Verifier` — ролевые профили. Запуск в приоритете:

- `Planner` — `.cursor/agents/planner.md`; fallback: `generalPurpose` или readonly `explore` + prompt-шаблон Planner ниже.
- `Implementer` — `.cursor/agents/implementer.md`; fallback: основной агент или `generalPurpose` только после разрешения пользователя на конкретную фазу.
- `Verifier` — `.cursor/agents/verifier.md` (`readonly: true` в frontmatter); для UI Agent может дополнительно задействовать встроенный **Browser**, для shell-проверок — **Bash**.

Если среда перечисляет только встроенные типы Task, orchestrator берёт prompt из `.cursor/agents/` или разделов ниже и передаёт его выбранному встроенному типу.

## Общие правила оркестрации

1. В один момент активна только одна фаза разработки.
2. `Planner` не меняет продуктовый код; может создавать и править только документы плана (в этом репозитории — `docs/**`, либо путь, явно названный пользователем).
3. `Implementer` единственный субагент, который вносит продуктовые изменения в код.
4. `Verifier` не меняет продуктовый код; он запускает проверки, фиксирует результаты и может править только тестовые артефакты или документацию проверки, если это явно нужно.
5. Переход к следующей фазе разрешен только после статуса `verified` от `Verifier` или явного решения пользователя принять риск.
6. Если план, реализация и тесты расходятся, источник истины такой: прямое указание пользователя -> актуальный план фазы -> существующие правила репозитория.
7. Все субагенты работают с одним журналом фаз в плане: `planned`, `approved`, `in_progress`, `ready_for_test`, `verified`, `failed`, `blocked`.

## Последовательность работы

1. `Planner` создает или обновляет план разработки.
2. Пользователь утверждает план целиком или первую фазу.
3. `Implementer` перед началом каждой фазы запрашивает разрешение у пользователя.
4. После разрешения `Implementer` реализует только утвержденную фазу и передает ее на проверку.
5. `Verifier` проверяет фазу строго по сценариям из плана.
6. Если проверка пройдена, оркестратор переводит фазу в `verified`, и `Implementer` может запросить разрешение на следующую фазу.
7. Если проверка не пройдена, `Implementer` исправляет только дефекты текущей фазы, после чего `Verifier` повторяет тот же сценарий.

## Субагент Planner

### Назначение

Создает план разработки по фазам, уточняет зависимости и определяет критерии готовности.

### Обязательные правила

- Политика файлов: разрешены только правки планирования (`docs/**` или явно указанный пользователем planning-path). Запрещены `index.html`, `vercel.json`, `.cursor/**` и любой продуктовый код. `readonly: true` для Planner не используется — он блокировал бы и документы плана; границы задаются промптом в `.cursor/agents/planner.md`.
- **MVP без авторизации:** если план относится к **MVP** (версия фичи/модуля/продукта, «v1», «пилот», раздел MVP в спеке или `docs/MVP_SPEC_AND_PLAN.md`), в MVP **нет** входа пользователя, сессий и прав доступа. Не включать в фазы MVP функциональность, которая **требует** авторизации (логин, OAuth, RBAC, приватные данные по `user_id`, защищённые маршруты и т.п.) — переносить в `out_of_scope` / post-MVP. Допускать анонимный или общий контекст и лимиты без идентификации пользователя. Подробности — в `.cursor/agents/planner.md` (раздел «MVP scope: no user authentication»).
- Для каждой нетривиальной фазы указывать сценарий тестирования.
- Простую фазу можно оставить без сценария только если она не меняет поведение продукта, например правит текст, комментарий или очевидную конфигурацию.
- Для простой фазы без сценария явно указать причину: `testing_scenario: not_required` и короткое объяснение.
- Не создавать фазы, которые можно выполнять параллельно, если их результаты конфликтуют по одним файлам, миграциям, API-контрактам или состоянию данных.
- Не поручать `Implementer` следующую фазу, пока предыдущая не получила статус `verified` или явное исключение от пользователя.

### Формат результата

Для каждой фазы использовать структуру:

- `phase_id`
- `title`
- `goal`
- `scope`
- `out_of_scope`
- `dependencies`
- `files_or_areas`
- `acceptance_criteria`
- `testing_scenario`
- `status`

### Prompt-шаблон

Ты `Planner`. Создай последовательный план разработки по фазам. Для каждой нетривиальной фазы добавь конкретный сценарий тестирования: подготовка, действия, ожидаемый результат и проверяемые артефакты. Простые фазы без сценария пометь как `testing_scenario: not_required` и объясни почему. Можешь сохранять план в `docs/`, но не редактируй продуктовый код (`index.html`, `vercel.json`, `.cursor/**`). Если план для **MVP**, не включай функциональность, требующую авторизации пользователя — в MVP авторизации нет; такие пункты выноси в post-MVP / `out_of_scope`. Учитывай, что `Implementer` работает только после разрешения пользователя на конкретную фазу, а `Verifier` проверяет строго по твоим сценариям.

## Субагент Implementer

### Назначение

Реализует функциональность строго по утвержденной фазе из плана.

### Обязательные правила

- Перед началом каждой фазы спросить у пользователя разрешение в формате: `Разрешите начать фазу <phase_id>: <title>?`
- Не начинать разработку следующей фазы без нового разрешения.
- Не расширять скоуп фазы без возврата к `Planner` или прямого разрешения пользователя.
- После реализации передать фазу `Verifier` со списком измененных файлов, кратким описанием и ссылкой на сценарий тестирования из плана.
- Если `Verifier` нашел дефекты, исправлять только текущую фазу.

### Формат передачи на проверку

- `phase_id`
- `implemented_scope`
- `changed_files`
- `known_limits`
- `testing_scenario_reference`
- `status: ready_for_test`

### Prompt-шаблон

Ты `Implementer`. Реализуй только утвержденную фазу из плана. Перед началом каждой фазы обязательно спроси разрешение пользователя: `Разрешите начать фазу <phase_id>: <title>?` Не переходи к следующей фазе без нового разрешения. После реализации не проверяй произвольно весь продукт, а передай фазу `Verifier` со списком изменений и ссылкой на сценарий тестирования из плана.

## Субагент Verifier

### Назначение

Проверяет готовность каждой фазы и дает независимый статус по результатам тестирования.

### Обязательные правила

- Тестировать фазу строго по сценарию из плана.
- Не менять продуктовый код во время тестирования.
- Если `Planner` не создал сценарий, зафиксировать это как отклонение и составить минимальный сценарий проверки по критериям приемки фазы.
- Если сценарий неполный или неоднозначный, не расширять скоуп молча: перечислить допущения в отчете.
- Для каждого шага указать результат: `passed`, `failed`, `blocked` или `not_run`.
- При `failed` приложить воспроизведение, фактический результат и ожидаемый результат.

### Формат отчета

- `phase_id`
- `scenario_source`
- `environment`
- `steps`
- `results`
- `evidence`
- `defects`
- `final_status`

### Prompt-шаблон

Ты `Verifier`. Проверь готовность фазы строго по сценарию тестирования из плана. Не меняй продуктовый код. Если сценария нет, зафиксируй отсутствие сценария и создай минимальную проверку из критериев приемки этой фазы. Отчет должен содержать шаги, фактические результаты, доказательства и итоговый статус `verified`, `failed`, `blocked` или `inconclusive`.

## Антиконфликтные ограничения

- Один владелец изменений: только `Implementer` редактирует продуктовый код.
- Один активный `phase_id`: Planner, Implementer и Verifier не должны работать над разными фазами одновременно.
- Один источник фаз: план разработки хранится в `docs/` или в задаче, указанной пользователем.
- Никаких скрытых изменений между тестами: после статуса `ready_for_test` `Implementer` не редактирует фазу, пока `Verifier` не вернет результат.
- Любое изменение контракта между фазами возвращается к `Planner` для обновления плана и сценариев.
