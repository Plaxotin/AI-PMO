# AI PMO — Аудит проектного плана и администратор поручений (MVP)

**Документ:** итоговая спецификация + план реализации + оценка стоимости по фазам  
**Версия:** 1.2  
**Дата:** 18 мая 2026  
**Репозиторий:** этот проект (корень — лендинг AI PMO; целевой код продукта — отдельный app-репозиторий по дорожной карте).

---

## Часть I. Итоговая спецификация (MVP)

### 1. Назначение и границы

**Продукт:** пользователь загружает файл плана (Excel/CSV), выбирает режим, получает за целевое время **интерактивный отчёт аудита** и **PDF**, без регистрации и без сохранения содержимого файла на сервере (stateless).

**В MVP входит:** `.xlsx`, `.xls`, `.csv`; парсинг и валидация на клиенте; **CPM и количественные метрики** — детерминированно; интерпретация, риски, оценка качества, рекомендации — через LLM; UI отчёта; PDF; демо-файл; лимиты Free; rate limit по IP/cookie. Отдельным модулем MVP — **BL-6 «Администратор поручений»** в полном объёме **v1.2** (`docs/SPEC-BL-6-assignments-admin.md`, фазы BL1-0 … BL1-5 в `docs/ASSIGNMENTS_ADMIN_CURSOR_PLAN.md`).

**В MVP не входит:** `.mpp`, Google Sheets, Stripe/Pro (допускается заглушка «скоро»), пакетный анализ, публичный REST API **аудита** как отдельного продукта для третьих сторон. **Аудит** остаётся без персистентности загруженных файлов. Для BL-1: **не входят** полная матрица мессенджеров, произвольная двусторонняя синхронизация переписки, юридически полное DLP/архивирование и интеграции с внешними таск-трекерами (допускается дорожная карта после MVP).

### 2. Пользовательские сценарии

| ID | Сценарий |
|----|----------|
| US-1 | Загрузка плана → полный аудит → отчёт + PDF. |
| US-2 | Акцент на критическом пути и узких местах. |
| US-3 | Сводка для руководства (KPI, вехи, ресурсы). |
| US-4 | Запуск на демо-файле без своего плана. |
| US-5 | Создание/редактирование поручения в реестре проекта; смена статуса и дедлайна. |
| US-6 | Просмотр списка поручений с фильтрами (статус, срок, ответственный). |
| US-7 | (Опционально MVP) Создание черновика поручения из входящего сообщения канала с подтверждением человеком. |

### 3. Режимы анализа

Режим задаёт **набор секций отчёта и объём LLM-промпта**. CPM и метрики считаются **всегда** (один проход на клиенте; на сервере — пересчёт из `tasks` для согласованности).

| Режим | Фокус |
|--------|--------|
| `full` | Все секции + полный PDF (целевой объём 8–15 стр.). |
| `critical_path` | CP, float, узкие места + минимальная сводка. |
| `errors` | Ошибки/конфликты и рекомендации. |
| `summary` | KPI и компактная сводка. |

По умолчанию: `full`. Переключение до кнопки «Анализировать».

### 4. Входные данные

- **Форматы:** `.xlsx`, `.xls` (SheetJS), `.csv` (PapaParse).
- **Поля:** название*, даты начала/окончания*, длительность, предшественники, % выполнения, ответственный, ресурс, веха, факт. даты, ID/WBS — по исходной спеке v0.1; обязательные валидируются.
- **Маппинг:** эвристика RU/EN → при неудаче **отдельный короткий LLM-вызов** только по именам колонок и **первым 5 строкам** → JSON маппинга. Без обязательных полей — ошибка с подсказкой.
- **Лимиты Free:** размер файла, max строк, анализов/день — константы в `lib/limits.ts`, проверка на клиенте и на сервере.

### 5. Стадии обработки (UI)

**State machine:** `IDLE → PARSING → VALIDATING → ANALYZING_API → RENDERING`.

| Стадия | Где | Содержание |
|--------|-----|------------|
| 1 | Клиент | Парсинг → нормализованные задачи. |
| 2 | Клиент | Валидация, лимиты. |
| 3 | Клиент | CPM (DAG, ES/EF/LS/LF, float, критический путь, при необходимости bottom-up %). |
| 3b | Сервер | LLM: ошибки, риски, баллы, рекомендации, язык; вход: `tasks`, `cpm_result`, `task_metrics`, `mode`, `locale`. |
| 4 | Клиент | HTML-отчёт + PDF. |

**Принцип:** числа CPM и **все количественные метрики** не генерируются и не изменяются LLM; модель только интерпретирует и формулирует.

### 6. Выход LLM (логическая схема)

- `plan_score`: overall + 5 критериев (completeness, dependencies, resources, milestones, timeline_realism).
- `errors[]`: severity, type, task_id, message, suggestion, **evidence**, **confidence** (checkpoint).
- `recommendations[]`, `risks[]`.
- Критический путь в UI: приоритет отображения из **`cpm_result`**; LLM не подменяет расчёт.

**Дисклеймер:** AI-анализ; рекомендуется верификация PM.

### 7. Количественные показатели по задачам (обязательно)

Модуль **`task_metrics`**, чистые функции + тесты. Набор «листовых» исполняемых задач и исключения суммарных задач — фиксируются в парсере; в отчёте строка «в расчёте N задач».

**Минимум MVP:**

| Метрика | Смысл |
|---------|--------|
| `overdue_total` | Просрочено (плановый финиш &lt; дата отчёта, выполнение &lt; 100%, нет своевременного факта; baseline — опционально отдельным полем). |
| `done_total` | Выполнено (100% или факт. окончание). |
| `no_predecessors` | Без предшественников (с исключением явного старта). |
| `no_successors` | Без последователей (с исключением конечных вех). |
| `not_started` | Не начаты. |
| `in_progress` | В работе. |
| `milestones_total` / `milestones_done` / `milestones_overdue` | Вехи. |
| `no_owner` | Без ответственного. |
| `invalid_dates` | Некорректные даты/длительность. |

Представление: блок KPI в HTML и в PDF с краткими определениями (tooltip / сноска).

### 8. API

**Аудит:** `POST /api/analyze` — тело: `tasks`, `mode`, `language` (опционально пересчитывать `cpm_result` и `task_metrics` **на сервере** из `tasks`).

Ответ: по выбранной интеграции (streaming или цельный JSON). Таймаут, retry, fallback-модель. Rate limit: 3/день/IP+cookie (Free).

**BL-1 (реестр):** REST под префиксом `/api/assignments` (или `/api/projects/:projectId/assignments`): создание, чтение, обновление, список с фильтрами; отдельный эндпоинт **вебхука** или **инжеста** для одного выбранного канала (если включено в релиз MVP). Аутентификация и авторизация по проекту — минимально достаточная для команды (см. §11). Rate limit и квоты — отдельные константы от аудита.

### 9. Технологии (целевой стек приложения)

Next.js 14 (App Router), React, Tailwind, shadcn/ui, SheetJS, PapaParse, Vercel AI SDK, `@react-pdf/renderer`, Recharts, Vercel. Рантайм-LLM продукта: абстракция провайдера (OpenAI / NVIDIA NIM и др. через совместимый base URL).

**BL-1:** персистентность (например **PostgreSQL** + Prisma/Drizzle на Vercel или внешний managed Postgres), очередь/крон для напоминаний по возможности (Vercel Cron + простая таблица outbox). LLM для извлечения полей из текста — только при включённом сценарии US-7 и с человеческим подтверждением.

### 10. Критерии приёмки (сжато)

**Аудит**

- Загрузка `.xlsx`/`.csv`, демо-файл.
- Парсинг на фикстурах; понятная ошибка без обязательных полей.
- CPM и метрики не из LLM; unit-тесты на графах и метриках.
- Отчёт: секции, checkpoint, дисклеймер, блок метрик.
- NFR: время, отсутствие персистентности файла, HTTPS.

**BL-1**

- CRUD поручений в рамках проекта; валидация обязательных полей; список с фильтрами (US-5, US-6).
- Аудит либо неизменён по NFR, либо явно разделён по доменам (нет утечки содержимого планов в таблицы BL-1).
- Если в релиз входит US-7: контракт JSON извлечения, сохранение сырого текста сроком хранения по политике, подтверждение перед публикацией в реестр.

### 11. BL-1 — Администратор поручений (в составе MVP)

**Назначение:** единый **реестр поручений по проекту** с актуальным статусом, дедлайнами и ответственными; подготовка к расширению входом из каналов и напоминаниями.

**MVP-объём (обязательный):**

- Модель поручения: `id`, `project_id`, `title`, `description` (опц.), `status` (enum: минимум `draft`, `open`, `done`, `cancelled`), `due_at` (опц.), `owner_id` / идентификатор инициатора, `assignee_ids` или строковые метки, `source` (`manual` | `import` | `webhook` — расширяемо), `created_at`, `updated_at`, `history` (журнал смен статусов — массив или отдельная таблица).
- UI: список, карточка, форма создания/редактирования; фильтры по статусу и дедлайну.
- API: см. §8; версионирование схемы ответа (header или query) при эволюции.

**MVP-объём (желательно, если укладывается в тот же релиз):**

- Один канал приёма (например **Telegram-бот** или **signed webhook** из Slack) → черновик поручения (US-7) с UI подтверждения.
- Напоминания: e-mail или сообщение в тот же канал за N дней/часов до `due_at` (константы + выключаемый флаг на проект).

**Принципы:** извлечение сущностей из свободного текста **не заменяет** явные поля в БД после подтверждения; PII и хранение сырья — по политике проекта (ретенция, маскирование в логах).

**Риски:** качество LLM-извлечения, согласование доступа к чатам, спам/дубликаты при вебхуках — закрываются идемпотентностью ключей, rate limit на инжест и ручным слиянием дубликатов в UI (минимум — пометка «возможный дубль»).

### 12. Подготовка к разработке фазы BL1-0 (рекомендации)

Перед кодом фазы **BL1-0** (контракты BL-1) имеет смысл закрыть подготовительный чеклист:

1. **Модель доступа:** кто создаёт проекты и поручения (один тенант / несколько команд / приглашения по email). Зафиксировать MVP-вариант (например один workspace на организацию + роли `admin` / `member`).
2. **Идентичность:** выбрать провайдера auth (Clerk, Auth.js, корпоративный SSO — что допустимо по срокам); минимум — сессия + привязка `user_id` к поручению.
3. **Данные:** выбор БД и региона; миграции; политика удаления проекта и каскада поручений.
4. **Интеграция с аудитом:** общий ли деплой и домен, общие ли пользователи; **запрет** смешивать бинарные/сырые загрузки планов с таблицами BL-1 на уровне политики продуктов.
5. **US-7 и каналы:** если не входит в первый релиз — явно отложить и не проектировать вебхук в BL1-0; если входит — один поставщик, тестовый бот/sandbox, секреты в env.
6. **Нефункциональные:** лимиты RPS на `/api/assignments`, базовый аудит действий (кто менял статус), дисклеймер про обработку персональных данных в поручениях.

## Часть II. План реализации

### Политика инструментов в Cursor

Требование **«разработка только в Composer»** **отменено** и не является частью спецификации. Допускается любая удобная комбинация **Agent**, **Composer**, **Chat**, инлайн-редактирования и ручных правок. Выбор режима — по типу задачи (см. таблицу в части III вместе с LLM).

**Ориентиры по режимам Cursor (не жёсткие правила):**

| Режим | Когда уместен |
|--------|----------------|
| **Agent** | многофайловые изменения, тесты, поиск по репо, «доведи фазу до зелёных тестов». |
| **Composer** | крупный согласованный дифф в нескольких связанных файлах за один запрос. |
| **Chat / Ask** | разбор ошибок, дизайн API, ревью без автоприменения. |
| **Инлайн** | точечные правки, переименования, мелкие фиксы. |

### Фаза 0 — Контракты

- `lib/types.ts` + Zod: `Task`, `AnalyzeRequest`, `AnalyzeResponse`, ответ маппинга колонок.
- `PROMPT_VERSION`, `lib/limits.ts`.
- Скелет `POST /api/analyze` с валидацией тела и заглушкой ответа.

### Фаза 1 — Парсинг и валидация (клиент)

- `lib/parser.ts`, эвристика заголовков, CSV.
- Map-LLM по первым 5 строкам при необходимости.
- `lib/validator.ts`, интеграция с прогрессом (стадии 1–2).

### Фаза 2 — CPM и метрики

- `lib/cpm.ts` + golden-тесты.
- `lib/task-metrics.ts` + тесты.
- Сервер: пересчёт `cpm_result` и `task_metrics` из `tasks` перед вызовом LLM (рекомендуется).

### Фаза 3 — LLM-анализ

- `lib/prompt.ts` (системный + user по `mode`/`locale`).
- `lib/llm.ts` (провайдер, JSON, retry, fallback).
- Слияние: итог отчёта = алгоритмические числа + вывод LLM без перезаписи чисел.

### Фаза 4 — UI отчёта

- Секции отчёта, Recharts, checkpoint, KPI метрик.
- Состояние `RENDERING`, ошибки API.

### Фаза 5 — PDF и демо

- PDF (включая блок метрик), `public/sample-plan.xlsx`.

### Фаза 6 — NFR и релиз

- Rate limit, отсутствие записи загрузок на диск, версия модели/промпта в метаданных без PII.
- Lighthouse по возможности; деплой; чеклист приёмки.

**Порядок в Cursor:** после каждой фазы — коммит; не смешивать крупные слои без зелёных тестов предыдущего.

### Трек BL-1 (администратор поручений)

Трек **можно вести параллельно** с аудитом после закрытия подготовки из §12 или **стартовать с BL1-0**, не дожидаясь релиза аудита, если команда и репозиторий разделены по модулям (общие только auth и деплой).

#### BL1-0 — Контракты и данные

- Zod + типы: `Project`, `Assignment`, `AssignmentStatus`, DTO списка/фильтров, ошибки API.
- Схема БД (миграция v1), индексы по `project_id`, `due_at`, `status`.
- Скелет `GET/POST/PATCH` под префиксом из §8; заглушка или read-only `Project` для локальной разработки.
- Решения из §12 зафиксированы в `docs/` или ADR (auth, тенант, ретенция).

#### BL1-1 — CRUD и авторизация

- Реализация эндпоинтов, проверка прав на `project_id`, журнал смен статусов.
- Seed-скрипт или фикстуры для e2e.

#### BL1-2 — UI реестра

- Список, карточка, формы; фильтры US-6; пустые состояния и ошибки сети.

#### BL1-3 — Telegram-инжест, STT, US-C, уточнения

- Обязательно в объёме BL-6 v1.2. См. `docs/SPEC-BL-6-assignments-admin.md`, `docs/ASSIGNMENTS_ADMIN_CURSOR_PLAN.md`, `docs/BL6_PRODUCT_DECISIONS.md`.

#### BL1-4 — Напоминания, публичный реестр (YOS), импорт/экспорт

- Обязательно в объёме BL-6 v1.2 (не опциональная фаза).

#### BL1-5 — Веб-загрузка US-C2, confirm UI, пилот

- Обязательно в объёме BL-6 v1.2. См. cursor-план фазы BL1-5.

## Часть III. Рекомендуемые LLM и режимы Cursor по фазам

Ниже — **модели для написания и сопровождения кода в Cursor** (не путать с **рантайм-LLM продукта** из §9: там допустимы OpenAI, NVIDIA NIM и др. по отдельному выбору). Названия моделей ориентировочные: подставляйте актуальные **frontier / Sonnet-уровень / mini** из каталога Cursor на дату работ.

| Фаза | Режим Cursor (типично) | Рекомендуемые модели (приоритет сверху вниз) | Заметка |
|------|-------------------------|-----------------------------------------------|---------|
| 0 — Контракты | Agent или Composer | **Claude Sonnet**, **GPT-4.1** / **GPT-4o**; для узких правок схем — **o4-mini** / **o3-mini** или быстрый аналог в каталоге | Мало кода, важна согласованность типов и Zod. |
| 1 — Парсинг, валидация | Agent | **Sonnet**, **GPT-4o**; упорные баги форматов/локалей — **Opus** или **GPT-4.1** | Много краевых случаев; Chat удобен для разбора одного падения. |
| 2 — CPM, метрики | Agent; для инвариантов — Chat | **o3** / **o1** или **Opus** (спецификация и доказательства); реализация и рефакторинг — **Sonnet** / **GPT-4.1** | Алгоритмы + golden-тесты; reasoning-модель — короткими сессиями. |
| 3 — LLM-анализ (код продукта) | Agent + Chat | **GPT-4.1** / **GPT-4o** или **Sonnet**; черновики промптов и политик merge — **Opus** / **o3** | Нужны устойчивый JSON и итерации промпта. |
| 4 — UI отчёта | Agent или Composer | **Sonnet**, **GPT-4o**; сложная вёрстка и состояние — **GPT-4.1** | Много компонентов; инлайн для мелких правок стилей. |
| 5 — PDF, демо | Agent | **Sonnet**, **GPT-4o**; капризный layout PDF — **Opus** точечно | `@react-pdf/renderer` часто требует нескольких итераций. |
| 6 — NFR, релиз | Agent; финальный проход — Ask/Chat | **Sonnet**, **GPT-4o**; предрелизный аудит безопасности/конфигов — **Opus** или **o3** | Больше чеклистов и ручных шагов Vercel. |
| BL1-0 — Контракты BL-1 | Agent или Composer | **Sonnet**, **GPT-4.1** / **GPT-4o**; схемы БД — **o3-mini** / быстрый аналог для ревью | Как фаза 0 аудита + миграции и ADR. |
| BL1-1 — CRUD, authz | Agent | **Sonnet**, **GPT-4o** | Классический серверный CRUD; Chat для edge cases прав доступа. |
| BL1-2 — UI реестра | Agent или Composer | **Sonnet**, **GPT-4o** | shadcn-паттерны как в фазе 4 аудита. |
| BL1-3 — Инжест, US-7 | Agent + Chat | **GPT-4.1** / **Sonnet**; промпт извлечения — **Opus** точечно | Близко к фазе 3 аудита по JSON/LLM. |
| BL1-4 — Напоминания | Agent | **Sonnet**, **GPT-4o** | Надёжность кронов и идемпотентность отправки. |

**Дополнительно:** **Gemini** (Pro / Flash) или другие модели из списка Cursor — разумны там, где у команды уже проверен качественный результат на TypeScript/React. **Локальные / «small»** модели — только для черновиков или поиска, не как основной движок фаз 2–3.

**Продуктовый рантайм (аудит плана для пользователя):** выбирается отдельно (например бесплатные **NIM**-endpoint с фильтром Free в каталоге NVIDIA, плюс fallback-модель); это не обязано совпадать с моделью, в которой пишется код.

## Часть IV. Оценочная стоимость реализации по фазам (Cursor + рекомендуемые LLM)

### Методика оценки

Стоимость складывается из:

1. **Подписка Cursor** — по сути фиксированная в месяц (например Pro ~20 USD, Ultra выше); все фазы делят один и тот же период разработки, поэтому **маржинальная** стоимость одной фазы в рамках Cursor **не линейна** — ниже даны **доли ожидаемого расхода лимитов** и **эквивалент в USD по API-ценам** тех же классов моделей (если бы аналогичный объём запросов оплачивался напрямую у провайдера). Это нужно для бюджета «сверх включённого».

2. **Переменная часть:** премиум-запросы сверх лимита (если включены в вашем плане), либо использование **Bring Your Own Key** — тогда цифры ближе к колонке «API-эквивалент».

**Допущения для цифр:** один разработчик; смесь **Sonnet** (основной объём) + **GPT-4o/4.1** (точечно) + **1–3 коротких сессии Opus/o3** на фазах 2–3 и при необходимости BL1-3; средняя сессия 1,5–2,5 ч активной работы с агентом; объём кода — полный MVP приложения (не лендинг), включая трек BL-1 в заявленном объёме §11.

### Человеко-время (для планирования, не деньги LLM)

Ориентир **чистого времени разработчика** с AI: фазы 0–1 ~**0,5–1,5** недели эквивалента; 2 ~**1–2**; 3 ~**0,5–1**; 4 ~**1–2**; 5 ~**0,5–1**; 6 ~**0,3–0,7** — сильно зависит от готовности репозитория и опыта. **BL-1:** BL1-0 ~**0,2–0,5**; BL1-1 ~**0,5–1**; BL1-2 ~**0,5–1,2**; BL1-3 ~**0,5–1**; BL1-4 ~**0,2–0,5** (недели эквивалента разработчика, не календарный SLA). Это не календарный SLA агента, а порядок величины для планирования людей.
