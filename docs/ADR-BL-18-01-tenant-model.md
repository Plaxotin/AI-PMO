# ADR-BL-18-01 — Модель тенанта и квота хранилища

**Статус:** принято  
**Дата:** 2026-05-24  
**Контекст:** спека BL-18 требует `tenant_id` и квоту **1 ГБ на тенант**; kickoff BL1-0 зафиксировал **один глобальный проект без мультитенанта**.  
**Связанные документы:** `docs/SPEC-BL-18-official-letter-generator.md` (§2, §8, §11), `docs/BL1-0_KICKOFF.md`, `docs/ADR-BL-18-02-production-decisions.md`.

---

## 1. Проблема

| Источник | Требование |
|----------|------------|
| SPEC-BL-18 §2, §8, §11 | Изоляция артефактов и квота **на тенант**; в аудите обязателен `tenant_id`. |
| BL1-0 kickoff п.2 | Один глобальный `project`, **без** организаций и мультитенанта. |
| Продуктив | Нужна предсказуемая модель до первого деплоя BL-18, без переделки аудита и storage. |

Без решения нельзя: считать квоту, выполнить критерий приёмки §11.1, согласовать RLS и пути в object storage.

---

## 2. Вариант A — полноценный мультитенант

### Суть

Вводится сущность **тенант** (организация / workspace). Пользователи привязаны к одному или нескольким тенантам через членство. Все артефакты BL-18 и записи аудита несут **реальный** `tenant_id`. Квота **1 ГБ** считается **отдельно для каждого тенанта**.

### Модель данных (минимум)

```
tenants (id, name, storage_quota_bytes, storage_used_bytes, created_at, …)
tenant_members (tenant_id, user_id, role: admin | member, …)
letter_templates (id, tenant_id, project_id?, version, …)
letter_storage_objects (id, tenant_id, bytes, purpose, expires_at?, …)
letter_audit_events (…, tenant_id, …)
```

Связь с BL-1 (опционально на старте, целевая):

```
projects.tenant_id → tenants.id
```

Пользователь в UI работает в **контексте выбранного тенанта** (или одного тенанта, если членство одно).

### Поведение квоты

- При `upload` шаблона / вложения / сохранении артефакта: `storage_used_bytes(tenant_id) + size ≤ storage_quota_bytes` (дефолт **1_073_741_824**).
- Превышение → HTTP **413** / код `TENANT_STORAGE_QUOTA_EXCEEDED`, в теле — лимит и по возможности **оставшийся объём**.
- Временные файлы (распаковка, AV) пишутся с `tenant_id` и **TTL**; байты входят в квоту до удаления (см. ADR-BL-18-02).

### Auth и админ тенанта

- Роль **`tenant_admin`**: повышение квоты (если разрешено конфигом), просмотр использования, удаление шаблонов организации (не чужих тенантов).
- Роль **`tenant_member`**: генерация писем, загрузка шаблонов в рамках политики продукта.
- RLS / проверки в API: любой запрос с `tenant_id` сверяется с членством текущего `user_id`.

### Плюсы

| # | Плюс |
|---|------|
| 1 | **Полное соответствие** SPEC-BL-18 и критериям приёмки §11 без оговорок. |
| 2 | Готовность к **нескольким организациям** на одном инстансе (типичный SaaS). |
| 3 | Аудит и расследования ИБ по организации естественны (`tenant_id` в логах). |
| 4 | BL-1 можно эволюционировать: `project` внутри `tenant`, без смены ключа квоты для писем. |

### Минусы и риски

| # | Минус / риск |
|---|----------------|
| 1 | **Больший объём работ** до первого prod: миграции, членство, UI выбора тенанта, RLS. |
| 2 | Нужна **политика онбординга**: кто создаёт тенант, invite, первый admin. |
| 3 | BL1-0 «один проект» нужно **дополнить** `tenant_id` или явной связью — иначе два параллельных мира доступа. |
| 4 | Тестирование и поддержка сложнее (граничные случаи: пользователь в 2 тенантах). |

### Когда выбирать A

- Планируется **несколько организаций** на одном деплое в горизонте MVP BL-18.
- Юридически / коммерчески продажа **«на организацию»** с изоляцией данных.
- Готовы параллельно довести **auth + членство** (не только скелет BL1-0).

### Оценка трудозатрат (техническая, не календарь)

- Схема + API + RLS: **средний** объём.
- UI контекста тенанта: **средний**.
- Миграция существующих пользователей (если уже есть): **низкий–средний** (один default tenant на всех — см. §5).

## 3. Вариант B — single-tenant deployment (синтетический тенант)

### Суть

На инстансе **ровно один** логический тенант. `tenant_id` — **константа** в конфиге (например совпадает с `DEFAULT_PROJECT_ID` или отдельный UUID в env `SINGLE_TENANT_ID`). Все пользователи делят **одну квоту 1 ГБ** на весь продукт. Таблица `tenants` может отсутствовать или содержать **одну строку**, создаваемую seed/migration.

### Модель данных (минимум)

```
-- опционально одна строка
tenants (id = SINGLE_TENANT_ID, storage_quota_bytes, storage_used_bytes)

letter_templates (tenant_id = SINGLE_TENANT_ID всегда)
letter_audit_events (tenant_id = SINGLE_TENANT_ID всегда)
```

Членство **не проверяется** (или все authenticated users = member). «Админ тенанта» из спеки — по сути **глобальный admin** инстанса (env/allowlist).

### Поведение квоты

- **1 ГБ на весь деплой**, не на организацию.
- Формулировка в UI: «лимит хранилища сервиса писем» (не «вашей организации»), если не врать про тенант.

### Плюсы

| # | Плюс |
|---|------|
| 1 | **Минимальные изменения** относительно BL1-0: тот же «один мир», один `project`. |
| 2 | Быстрее вывести **пилот / внутренний prod** на одну команду. |
| 3 | Поля `tenant_id` в аудите **заполняются** — схема событий совместима с будущим A. |
| 4 | Меньше UI (нет переключателя организации). |

### Минусы и риски

| # | Минус / риск |
|---|----------------|
| 1 | **Расхождение с буквой спеки** §2 («на тенант» = на организацию): нужна явная оговорка **режима развёртывания** `SINGLE_TENANT_MODE=true` в документации и конфиге. |
| 2 | Второй клиент на том же инстансе **без деплоя** невозможен — общая квота и общие шаблоны (если не ввести project-scoped ACL отдельно). |
| 3 | При переходе на A потребуется **миграция квоты и объектов** (разрез одного bucket по новым tenant_id). |
| 4 | Критерий приёмки для **внешнего заказчика** «квота на организацию» **не выполняется** без смены режима. |

### Когда выбирать B

- **Единственный заказчик** на выделенном инстансе (on-prem / dedicated Vercel project).
- Пилот на 1–2 недели с обязательством **не подключать вторую организацию** на том же URL.
- Команда откладывает онбординг организаций до BL-18 v1.1.

### Оценка трудозатрат

- Схема с константой `tenant_id`: **низкий**.
- Риск технического долга при росте: **высокий**, если B затянется.

## 4. Сравнительная таблица (A vs B)

| Критерий | A — мультитенант | B — single-tenant |
|----------|------------------|-------------------|
| Соответствие SPEC-BL-18 «1 ГБ на тенант» | Да, буквально | Только при **одной организации на инстанс**; иначе нет |
| Изоляция данных между организациями | Да | Нет |
| `tenant_id` в аудите §8 | Реальный | Константа (валидный UUID) |
| Совместимость с BL1-0 «один project» | Через `tenant_id` на project или default tenant | Прямая |
| UI | Выбор/контекст тенанта | Не нужен |
| RLS / authz | Членство + роли | Упрощённо: любой login |
| Второй заказчик на том же URL | Да | Нет (без миграции на A) |
| Трудозатраты до prod | Выше | Ниже |
| Техдолг | Ниже | Выше при росте |

## 5. Рекомендация для продуктива AI PMO

**Принято: вариант A в режиме «один тенант по умолчанию» (A₀)** — не путать с вариантом B.

| Аспект | Решение A₀ |
|--------|------------|
| Схема | Таблицы `tenants`, `tenant_members` **всегда** в prod-миграции BL-18. |
| Первый деплой | Seed: один тенант `Default Organization`; все новые пользователи → `tenant_members` с ролью `member`; первый пользователь или env-список → `tenant_admin`. |
| Квота | **1 ГБ на этот тенант**; при появлении второго тенанта — отдельная квота без смены схемы. |
| Конфиг | `DEPLOYMENT_MODE=multi_tenant` (default) или `single_tenant` только для **выделенных** инстансов (вариант B как **явный** флаг, см. ADR-BL-18-02). |
| BL1-0 | `projects` получает nullable `tenant_id` (backfill default tenant); до миграции BL-1 — `project_id` в письмах опционален, `tenant_id` обязателен. |

**Вариант B** допустим **только** если в runbook деплоя зафиксировано: `DEPLOYMENT_MODE=single_tenant`, один заказчик, в спеке §2.1 читается как «квота инстанса». Для **публичного SaaS AI PMO** — **не использовать B**.

## 6. Согласование с BL1-0 (снятие конфликта)

| Элемент BL1-0 | Действие при A₀ |
|---------------|-----------------|
| Один `DEFAULT_PROJECT_ID` | Сохраняется; проект привязывается к default `tenant_id`. |
| «Без мультитенанта» в kickoff | Уточнение: **нет мультитенанта в UI BL1-0**; платформа BL-18 вводит тенант **раньше**, BL-1 догоняет. |
| Auth skeleton | Обязателен **в prod** для BL-18: без сессии генерация запрещена (401). |

Файл `docs/BL1-0_BL18-ALIGNMENT.md` фиксирует поля и порядок миграций.

---

## 7. Последствия для реализации

1. Миграция `2026xxxx_bl18_tenants.sql`: `tenants`, `tenant_members`, счётчик `storage_used_bytes`.
2. Object storage: префикс ключей `{tenant_id}/letters/...`.
3. Каждый route BL-18: резолв `tenant_id` из сессии (активный тенант) или из membership по `project_id`.
4. Env: `DEFAULT_TENANT_ID` (seed), `DEPLOYMENT_MODE`, `TENANT_STORAGE_QUOTA_BYTES` (override 1 GiB).
5. При `single_tenant`: пропуск UI выбора, `tenant_id = DEFAULT_TENANT_ID` — поведение как B, но **таблица tenants есть** для миграции на multi без смены audit schema.

---

## 8. Критерии пересмотра ADR

- Появление второго заказчика на одном инстансе при `single_tenant` → обязательный переход на `multi_tenant` (A₀).
- Требование регулятора: физическое разделение БД по тенантам → отдельный ADR (шардирование), не отменяет логическую модель A.
